# Auto-amend review findings with severity-based policy

## Goal

After `/z-review-all` runs its consultants and aggregates findings into `findings.md`, the final output currently requires the user to manually review `REVIEW-TASKS.md` and run `/z-amend` (for spec gaps) or `/z-implement-all` (for fixup tasks). This wastes tokens asking "do you want to amend?" every time.

Change the flow so amendments are applied **automatically** based on severity, with the user only consulted for confirmed-borderline cases.

## Policy

- **🔴 Blocker (severity: blocker)** — auto-amend. Skip user gate. These are correctness issues; amend immediately.
- **🟡 Major (severity: major)** — auto-amend. Skip user gate. The review's pushback already validated them. If the amendment is genuinely ambiguous enough to question, it wouldn't be major — it'd be an escalation.
- **🟢 Minor (severity: minor)** — auto-amend. Minor findings in REVIEW-TASKS.md get amended without asking.
- **Escalations / premise_failure** — these already surface via their own mechanism. Leave as-is (user decides).
- **Report-only observations** — leave in findings.md only, as they are now.

The user CAN still opt out after the fact via git (amendments are applied to plan artifacts, not committed code). The commit message will say "auto-amended: <N> findings" so the rollback path is clear.

## Files to edit

### `commands/z-review-all.md` (command version)

**Phase 6** currently builds `REVIEW-TASKS.md` and snapshots it. After Phase 6 and before Finalize, add a new phase or inline step that:

1. Reads `$BASE/REVIEW-TASKS.md`
2. Parses out all `amendment_proposal` items (those with `**Class:** spec_gap`) and `candidate_task` items (those with `**Class:** implementation_drift`)
3. For **blocker** amendment proposals → call `/z-amend "<specific amendment>"` directly via the driver's command invocation mechanism (not via subagent — inline, same session)
4. For **major** amendment proposals → same auto-amend
5. For **minor** amendment proposals → same auto-amend
6. For **candidate fixup tasks** (implementation_drift, any severity) → these stay as `REVIEW-TASKS.md` for `/z-implement-all`. Do NOT auto-implement — user still reviews and deletes candidates before running implement-all. Reasoning: implementation changes produce actual code diffs, not plan artifact edits.
7. After auto-amending, verify the amendments landed (re-read the spec/plan/tasks) and log an `auto_amend_applied` event for each.

**Hard rules to add to this new step:**
- Do NOT ask the user "do you want to amend?" for blocker/major/minor amendment proposals. Just do it.
- Do NOT auto-amend if the amendment would touch a `[x]` (completed) task — that requires user disposition. Those stay in REVIEW-TASKS.md as superseding_task items.
- Do NOT auto-implement code changes — only auto-amend plan artifacts.
- Log everything: write `$BASE/archive/$RRUN/auto-amend-log.md` with a per-amendment entry showing what was amended, the finding source, and the `/z-amend` command that was used.

### Existing amend flow

The `/z-amend` command already has Phase 4 (user gate) that asks "Approve as drafted / Revise / Abandon". This gate must still fire when `/z-amend` is called standalone. But when invoked from the review-all auto-amend flow, it should be **skipped** — the review already validated the finding.

Add a `--skip-user-gate` flag to `/z-amend`:
- When present (`--skip-user-gate`), Phase 4 (AskUserQuestion for approval) is skipped. The amendment proceeds directly from Phase 3 (impact analysis) to Phase 5 (consult, if triggered) then Phase 6 (propagate edits).
- When absent (normal invocation), Phase 4 runs as it does today.
- The flag is documented in the command's frontmatter and argument-hint.

### `commands/z-amend.md` and `skills/z-amend/SKILL.md`

Add `--skip-user-gate` support to both.
