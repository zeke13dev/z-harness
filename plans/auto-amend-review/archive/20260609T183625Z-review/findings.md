### Severity: minor (worth noting for future plans)

- [self-review] **Dependency ordering between amendment proposals is not addressed.** If two amendment proposals have a `**Depends on:**` link, Phase 6.5 processes them in document order. Serial processing naturally handles most cases, but there's no explicit topological sort. In practice, dependencies between amendment proposals in the same review run are exceedingly rare. **Pushback:** `/z-amend` handles its own dependency resolution internally — if proposal B's amendments touch files modified by proposal A, the impact analysis in Phase 2-3 would detect the changed state.

- [self-review] **Re-run idempotency is not addressed.** If Phase 6.5 is interrupted after some amendments are applied, re-running `/z-review-all` rebuilds REVIEW-TASKS.md from unchanged findings.md and re-applies the same amendments. `/z-amend` would encounter already-applied changes and either no-op or fail. **Pushback:** The TASK.md addresses rollback path (git). A checkpoint marker would be a nice-to-have but the failure mode (z-amend no-ops) is safe — it wouldn't corrupt state.

- [self-review] **The slug for the inner `/z-amend` invocation is implicit.** Phase 6.5 says to invoke `/z-amend --skip-user-gate "<amendment text>"` and "Follow the `/z-amend` pipeline for this slug." The context establishes that `this slug` = `$Z_HARNESS_SLUG`. **Pushback:** The orchestrator LLM running review-all would pass the slug as part of invoking the z-amend pipeline — this is a documentation clarity gap, not a behavior gap.

- [self-review] **No per-severity opt-out config.** The policy auto-amends all three severities equally. A user with a preference for manual review of minor spec changes has no opt-out per-run — only git rollback after the fact. **Pushback:** The TASK.md acknowledges this: "The user CAN still opt out after the fact via git." A future iteration could add `Z_HARNESS_AUTO_AMEND_SEVERITY=blocker,major`.

- [self-review] **Template `<slug>` in auto-amend-log.md is not explicitly bound to `$Z_HARNESS_SLUG`.** The context makes it unambiguous for the executing agent. **Pushback:** This is a documentation precision gap — the agent context always has the slug available.
