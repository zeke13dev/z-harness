## Prong A — Implementation drift

### Severity: blocker

- **[both]** `commands/z-implement-all.md:773` final `phase_end` uses field names `candidates_accepted` / `candidates_skipped` and omits `wall_ms` + `edited`, while `commands/z-review-all.md:447` uses `accepted` / `edited` / `skipped` / `wall_ms`. The two parent commands emit divergent shapes for the same logical event (`phase_end` for `name: memory_review`). Any `/z-stats` jq filter or downstream tool expecting one shape will silently miss the other.
  - **One-reason-it-might-be-wrong:** if `/z-stats` only ever filters by `kind == "phase_end"` and presents whatever fields exist, the divergence is cosmetic and not a parse failure. Verified: `/z-stats` Phase 2 groups by `phase` name but doesn't introspect inner fields — so this is "cross-task drift" in the strict sense (different shape for the same logical event) but doesn't break the consumer today. Still a real contract bug for v2 / future consumers.

### Severity: major

- **[both]** `index_path` was added as the 7th caller-input field in `agents/review-agent.md:20` and is hardcoded in `commands/z-implement-all.md:642` and `commands/z-review-all.md:407`, but `z-harness/plans/memory-self-improve-loop/SPEC.md:48-53` still lists only 6 inputs. The implementation moved ahead of the spec during T003's revision cycle and SPEC was never backfilled. Future readers will be confused about whether `index_path` is required.
  - **One-reason-it-might-be-wrong:** SPEC was last edited in T001 to add the known-consultation-gap section; the `index_path` addition was a T003 reviewer-fix that legitimately could have been called out as a SPEC amendment (Prong B), not implementation drift. Either framing is valid; promoting once is sufficient.

- **[codex]** `commands/z-review-all.md:434-437` documents the Accept-failure path in prose ("On `STATUS: skipped` or `STATUS: bad_input`, log `review_agent_suggest_failed`") but provides no bash snippet for the log call, while `commands/z-implement-all.md:748` has the full bash. Future copy-paste implementers won't see the exact event payload to emit.
  - **One-reason-it-might-be-wrong:** review-all's prose may be intentionally terse since the same structure is documented verbatim in implement-all 60 lines earlier in the same repo; readers can cross-reference. Counter: a forked z-review-all skill would lose the cross-reference. Worth fixing.

- **[both]** Event-kind reference table at `commands/z-implement-all.md:777-787` is missing `review_agent_suggest_failed` and `review_candidate_skipped`. The same table in `commands/z-review-all.md:454-460` correctly includes both. The table is documentation, not code — events are still emitted — but the docs claim to be exhaustive.
  - **One-reason-it-might-be-wrong:** the events are visible in the code body of Phase 9 above the table; the table may be intended as a quick-reference rather than authoritative. Counter: if it's not authoritative it should be removed or labeled.

  - **One-reason-it-might-be-wrong:** the orchestrator always `cd`s to repo root at Setup step 1; the relative path is effectively always relative to repo root and always resolves. Real risk is near-zero. But the contract drift is real — fix is one `$(pwd)/...` away.

## Prong B — Spec gaps

### Severity: blocker (spec must be corrected before shipping)

None. All Prong B findings are major/minor.

### Severity: major (spec should be amended; existing implementation may stand)

- **[both]** `--from-candidate-json` flag contract is referenced in SPEC.md:158-159 ("dispatch `/z-suggest-memory` … via the existing CLI") but SPEC never specifies:
  - which phases of `/z-suggest-memory` are bypassed (3a–3f per skill file, but SPEC doesn't say so);
  - whether `--concept` is inferred from `suggested_concept_slug` or required separately;
  - which phases still run (Phases 4–6: validation, atomic write, MEMORIES-FLAT regen — per skill file).
  - **One-reason-it-might-be-wrong:** the contract IS fully specified in `skills/z-suggest-memory/SKILL.md` (T002 + T009 edits). SPEC.md leaning on the skill file for detail is consistent with the "two-tier docs" pattern (commands/skills are the LLM tier, SPEC is the human tier). Counter: SPEC.md is the authoring contract for this plan; it should at minimum link to the skill file's `--from-candidate-json` section.

- **[codex]** SPEC.md failure-mode section (around line 200+) doesn't enumerate `review_agent_suggest_failed` — the event that fires when an Accept dispatch to `/z-suggest-memory` itself fails (bad schema, validation error). It's emitted in implementer code but never pre-spec'd.
  - **One-reason-it-might-be-wrong:** this event is a downstream-failure mode that the spec couldn't have anticipated without specifying the full /z-suggest-memory error contract — which is out-of-scope for this plan's SPEC. Fair counter; mark as observation rather than a fix.

### Severity: minor (worth noting for future plans)

- **[codex]** SPEC's `all_tasks_skipped` skip-condition is ambiguously named: the implementation in `scripts/run-memory-review.sh:72-85` checks for "zero `[x]` in TASKS.md" which equally matches "no tasks executed yet" — not literally "all tasks were user-skipped." Rename or add a sentence of clarification.
  - **One-reason-it-might-be-wrong:** in practice `/z-implement-all` cannot reach Phase 9 unless the run has terminated, so "zero `[x]`" really does mean "nothing happened" — the naming is just imprecise. Minor.

- **[codex]** SPEC doesn't specify when the `edited` counter increments (once per Edit, or once per Edit→Accept, or after user confirms the edit). Implementation today is implicit.
  - **One-reason-it-might-be-wrong:** v1 metric is descriptive rather than load-bearing; specifying it precisely now is over-engineering. Defer.

- **[gemini]** SPEC.md lacks a "v1 limitations" section that PLAN.md has. Future readers (or v2 amendments) won't see the deferred-by-design list without cross-reading PLAN.md.
  - **One-reason-it-might-be-wrong:** SPEC ↔ PLAN cross-referencing is the harness norm. Counter: SPEC is what survives the longest; lifting a "Non-goals (v1)" mirror into SPEC costs nothing and prevents v2 confusion.

- **[gemini]** Edit UX in SPEC.md:157-159 is one sentence ("Surface fields, collect edits, re-present as Accept") — doesn't say which fields are editable, whether tags are comma-separated or array, what happens if text exceeds the 280-char cap during edit.
  - **One-reason-it-might-be-wrong:** AskUserQuestion is constrained enough that the implementer's reasonable interpretation works in practice. Defer until first user complaint.
