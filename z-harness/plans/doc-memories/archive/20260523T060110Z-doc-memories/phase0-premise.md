# Phase 0 — Premise

## Inputs

- BRAINSTORM.md (chosen_framing: codex, with Claude sequencing amendment)
- No RESEARCH.md
- No docs/llm/INDEX.json in z-harness itself (relevant for dogfooding)

## Premise as I read it

Two interlocking gaps in the current two-tier docs system:

1. **Content gap.** `docs/llm/<slug>.json` carries `invariants` and `gotchas` as short strings without provenance, kind, or date. It has no slot for "we tried X and dropped it because Y", incident context, decision rationale, or performance traps. Code preserves the survivor only; this metadata lives nowhere.
2. **Lookup gap.** doc-fetcher's INDEX.json substring match is brittle for intent-based queries. When a memory exists but the query vocabulary diverges from the slug/summary, the fetcher returns `no_match` and the orchestrator falls through to Explore (expensive).

The Codex framing addresses both by (a) adding a typed `memories` array to per-concept JSON with `type / text / source / date / tags`, (b) compiling a flat `docs/llm/MEMORIES-FLAT.md` artifact that ripgrep can scan, and (c) adding MEMORIES-FLAT.md grep as a *second phase* in doc-fetcher (Claude amendment — INDEX.json substring stays as the cheap first phase). Authoring is hooked into `/z-debug` and `/z-improve` retros via a new `/z-suggest-memory` skill.

## Premise concerns surfaced and resolved

- **Dogfooding.** z-harness has no `docs/llm/` of its own; we can't exercise the new lookup logic against its own output. **User decision:** ship blind, dogfood later in a target repo (e.g. qt-bot) via manual validation post-merge. The plan does NOT add a `/z-init-docs` pass for z-harness as a prerequisite. Acceptance criteria must therefore lean on unit-style tests against a small synthetic fixture rather than end-to-end validation against real docs.
- **Authoring trigger.** All three ideators flagged authoring burden as the #1 risk. **User decision:** `/z-suggest-memory` is a mandatory prompt in `/z-debug` post-mortem and `/z-improve` retro phases. It may emit zero memories if nothing salient — the mandatory part is the *call*, not the *result*. `/z-plan` is NOT extended (no new abandoned-path retro phase) — this keeps `/z-plan` scope contained.
- **Synthesis cap.** doc-fetcher's ≤2 KB output cap is the *output* limit. MEMORIES-FLAT.md is unbounded raw input that ripgrep filters cheaply locally; the doc-fetcher still summarizes hits into its ≤2 KB return. This is consistent with the existing contract and does not require relaxing the cap.
- **Schema migration.** Existing `invariants` and `gotchas` short-string fields stay alongside the new `memories` array (per user-choice section: "do not deprecate them as Gemini suggested"). All existing `docs/llm/<slug>.json` files remain valid without a `memories` field; doc-fetcher and `/z-maintain-docs` treat `memories: []` as the default.

## What I take the goal to be

Ship a backward-compatible enrichment of the two-tier docs system that:
- Adds a typed, dated, provenance-bearing `memories` array to per-concept `docs/llm/<slug>.json`.
- Compiles and maintains `docs/llm/MEMORIES-FLAT.md` as a ripgrep-friendly flat artifact, regenerated by `/z-maintain-docs` and `/z-init-docs`.
- Extends `doc-fetcher` with a second-phase ripgrep over MEMORIES-FLAT.md (after the existing INDEX.json substring match), with substring fallback when `rg` is absent.
- Adds a `/z-suggest-memory` skill, called mandatorily from `/z-debug` post-mortems and `/z-improve` retros.
- Extends `doc-updater` to extract memories into a `## Memories` section of `docs/human/<slug>.md` for two-tier sync.

Out of scope (explicit non-goals):
- Embedding search / vector index.
- Dedicated `docs-search` agent (the Codex framing keeps `doc-fetcher` as the single retrieval surface).
- Deprecating `invariants` / `gotchas` short-string fields.
- Bootstrapping z-harness's own `docs/llm/` (separate effort).
- A `/z-plan` abandoned-path retro hook (rejected to keep `/z-plan` scope contained).

Premise accepted — proceeding to exploration.
