### (1) Framing
The central tension is between the need for a universally applicable, repo-agnostic toolchain (`z-harness`) and the project-specific necessity of querying noisy, domain-specific external APIs (like Kalshi or weather services in `qt-bot`). The main orchestrator thread is currently hemorrhaging tokens on verbose HTTP responses, paginated JSON, and unstructured HTML. We must determine whether the solution is a generic "web-fetcher" built into z-harness, or if domain-specific lookups fundamentally require a bespoke agent living entirely within the target repository.

### (2) Core hypothesis
We should build a generalized `external-researcher` (or `lookup-agent`) primitive into `z-harness` powered by Haiku, but architect it strictly as an extensible plugin runner. This agent will inherently possess generic web-search and page-fetching tools. However, to maintain z-harness's repo-agnostic mandate, domain-specific capabilities (like Kalshi queries) will be injected dynamically from the target repository's `.z-harness/plugins/` or `skills/` directory at runtime. The Haiku agent's sole mandate is to execute these tools, parse the bloated responses in a throwaway context, and return a highly condensed, cited synthesis (<= 2KB) to the main thread.

### (3) Risks
- **Parsing capability:** Haiku might struggle to reliably navigate heavily nested JSON or complex paginated schemas without highly specific, domain-aware prompting, leading to dropped critical details (e.g., missing a payout edge case).
- **Tool injection complexity:** Dynamically mounting target-repo tools into a generic z-harness subagent introduces a fragile boundary. If a local `qt-bot` script fails or changes signature, the generic agent might spin uselessly.
- **Scope creep:** A generic web-researcher might be tempted to "solve" the problem rather than just fetch and synthesize, wasting its own token limit on unnecessary reasoning.

### (4) Plan implications
- Create a new agent definition (e.g., `agents/external-lookup.md`) utilizing Haiku.
- Equip this agent with standard web and HTTP tools natively.
- Develop a dynamic tool-loading mechanism in z-harness that allows target repos to expose specific read-only shell scripts or CLI tools to this subagent.
- The prompt must heavily enforce strict synthesis limits (e.g., "Return NO MORE than 300 words. Strip all raw JSON. Only answer the explicit query.").
- Update documentation (`docs/llm/agents.json`) to establish the pattern: "Main thread never curls; always dispatch `external-lookup`".

### (5) What would change my mind
- If we discover that synthesizing unstructured web HTML (docs) and querying structured API endpoints (Kalshi) require vastly different system prompts or model tiers, forcing them into a single `external-lookup` primitive would be a mistake.
- If injecting local tools proves too architecturally complex for z-harness, it would be better to simply provide a *template* for a lookup agent that users copy directly into their target repository's local agent definitions.
