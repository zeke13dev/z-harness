## Framing

The problem is not "should we fetch externally" — it's "who bears the context cost of exploration." Right now the main agent thread is doing double duty: it is both the orchestrator (stateful, expensive, needs to stay coherent across the whole task) and the explorer (stateless, disposable, just needs to return a fact). The lookup subagent idea is simply applying the same separation already applied to internal docs (doc-fetcher) and remote state (remote-runner). The question is whether it belongs in z-harness core or stays repo-specific. The answer hinges on a single distinction: is "external lookup" a universal orchestration primitive, or is it a domain capability that z-harness happens to need wiring for?

## Core hypothesis

Build a thin, repo-agnostic `external-fetcher` agent in z-harness core with a single responsibility: accept a natural-language query + a tool whitelist (WebFetch, Bash with curl, or domain-specific CLI), perform the exploration in fresh context, and return a <=2 KB synthesis. The agent is model-tier Haiku (it does no reasoning, just extraction). Domain specifics (Kalshi CLI flags, weather API endpoints, etc.) are injected at dispatch time via the tool whitelist and a `context:` field — not baked into the agent. This keeps z-harness repo-agnostic while giving qt-bot (and any other target repo) a reusable primitive.

## Risks

- **Synthesis quality at Haiku tier.** Haiku is cheap but may produce poor signal-to-noise on noisy HTML or paginated API responses. The agent needs a strict output contract: structured fields only, no prose dump. If Haiku fails to compress, the orchestrator gets garbage instead of nothing.
- **Tool whitelist sprawl.** If every lookup variant declares its own tool set (WebFetch for docs, Bash+curl for Kalshi, SSH for remote data), the agent spec fragments into many flavors. Each flavor needs a separate agent file or a dispatch-time override mechanism that doesn't yet exist.
- **No caching layer.** The same Kalshi ticker query will spin up a fresh Haiku subagent on every run. If the user runs six tasks in a day touching the same ticker, that's six subagent calls for identical data. A thin in-process cache (keyed on query hash) would eliminate most real-world cost.
- **Scope creep into write territory.** An external-fetcher that can run arbitrary Bash is one flag away from writing. The agent must refuse write verbs as explicitly as remote-runner does — otherwise it becomes a footgun.
- **z-harness / qt-bot boundary.** If the lookup logic lives in z-harness core but the CLI tools (Kalshi client, weather API wrapper) live in qt-bot, the subagent needs the target repo's environment to be set up before dispatch. That coupling is non-trivial to enforce.

## Plan implications

- Add `agents/external-fetcher.md` to z-harness core: Haiku, tools: WebFetch + Bash (curl/jq only, no writes), output contract: <=2 KB synthesis with structured fields.
- Add dispatch protocol: caller provides `query`, `tool_whitelist` (enum), and optional `context` blob. Agent returns `STATUS: ok | no_result | error` + synthesis.
- Export the agent to all target-repo formats (Cursor, Codex, Agy) via the existing multi-ide-export pipeline.
- Update orchestrator guidelines (CLAUDE.md, skills) to say: "before issuing WebFetch or domain-API calls from main thread, dispatch external-fetcher."
- For qt-bot specifically: add a qt-bot-specific dispatch wrapper (skill or skill argument) that pre-populates the Kalshi/weather context blob so callers don't repeat it every time.

## What would change my mind

- If Haiku reliably cannot compress noisy HTTP responses to <=2 KB without losing the key fact, then the tier should be Sonnet — which makes the cost argument much weaker.
- If the tool whitelist mechanism cannot be kept narrow (i.e., the agent ends up needing arbitrary Bash), then the risk of write-footgun outweighs the token savings.
- If a simple in-process MCP tool (WebFetch with a prompt wrapper) already satisfies the use case with no new agent infrastructure, the subagent is over-engineering.
