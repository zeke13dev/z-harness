## Framing

This should be generalized as a z-harness primitive, not qt-bot-specific.

The repeated pain is not “Kalshi lookup.” It is “main-thread context pollution from exploratory external retrieval.” Kalshi is just the sharpest current instance. Weather markets, library docs, exchange metadata, API schemas, release notes, pricing tables, and tool documentation all have the same shape: high-noise retrieval followed by small, source-backed synthesis.

The primitive should be named by behavior, not domain: `external-lookup` or `lookup-researcher`, not `kalshi-finder`.

It should be explicitly dispatched by skills or the main agent, never auto-routed. Its contract is: go fetch noisy external/domain data in fresh context, discard the noise, return a compact cited answer with enough provenance that the main agent can act.

## Core hypothesis

The right shape is a cheap, constrained Haiku subagent with a pluggable lookup profile.

Base agent:

- Model: Haiku
- Purpose: external read-only retrieval and synthesis
- Tools: web/search/fetch plus shell only if needed for safe read-only CLI/API calls
- Output cap: probably `<=2KB` by default, `<=4KB` with explicit expansion
- Required output: answer, evidence, uncertainty, next query if blocked
- Forbidden: implementation, repo edits, speculative planning, domain decisions beyond lookup

Profile examples:

- `profile: web-docs`
- `profile: kalshi`
- `profile: weather-markets`
- `profile: generic-api`
- `profile: npm-package-docs`

z-harness owns the primitive and contract. Target repos own optional profiles, credentials, endpoint conventions, and domain-specific examples.

So qt-bot could export a Kalshi lookup profile into the agent prompt or skill wrapper, but the underlying agent remains repo-agnostic.

## Risks

The main risk is creating a vague “research agent” that starts doing analysis, planning, and implementation thinking under the cover of lookup. That would recreate the context problem with a new boundary.

The second risk is credential and side-effect leakage. Domain APIs can look read-only while hiding stateful endpoints, auth refresh, order placement, or rate-limit mutation. The agent needs a hard read-only tool policy and probably endpoint allowlists for sensitive domains like Kalshi.

The third risk is false compression. A tiny synthesis can omit the one field that matters later: settlement rule, market close time, timezone, ticker date convention, payout denomination, pagination limit, API version, or docs version. The output schema must force “operationally relevant fields,” not just “answer.”

The fourth risk is premature generality. If the abstraction starts with adapters, registries, schema languages, and profile discovery, it will become heavier than the problem. Start as a Markdown agent contract plus a few profile snippets.

## Plan implications

Add one z-harness core agent, likely `agents/external-lookup.md`.

Its prompt should define:

- read-only external retrieval
- explicit dispatch only
- strict output budget
- source citation requirements
- uncertainty reporting
- refusal for writes, trades, mutations, account actions, and secrets exposure
- profile mechanism supplied by caller or target repo

Add a small skill-facing convention:

```text
Task:
Profile:
Question:
Known context:
Required fields:
Acceptable sources/tools:
Output budget:
```

For qt-bot, add a domain wrapper later, probably not in z-harness core:

```text
Use external-lookup with profile kalshi-market-lookup.
Return ticker, series, event title, market title, close time, settlement rule, API source, and confidence.
```

This preserves z-harness as the primitive layer while allowing qt-bot to become very good at Kalshi lookup without contaminating every other repo.

## What would change my mind

I would make it qt-bot-specific first if Kalshi lookup requires privileged repo-local code, private credentials, nontrivial normalization, or domain invariants that cannot be expressed safely as a lightweight profile.

I would avoid building it at all if most lookups require high-level judgment rather than retrieval compression. If the value is mostly “interpret this ambiguous market strategy,” that belongs in a Sonnet consultant or planner, not a Haiku lookup agent.

I would make it Sonnet instead of Haiku only if the lookups routinely involve messy source reconciliation across conflicting docs, dynamic pages, hidden API conventions, or schema inference where cheap compression produces wrong operational answers.

I would generalize harder only after seeing three distinct successful profiles: Kalshi market lookup, live library docs lookup, and one non-Kalshi domain API lookup.
