# Brainstorm: doc-memories

## Framing: Claude

### Framing
The two-tier docs system conflates two distinct jobs — *locating* (where is the code?) and *remembering* (what did we learn the hard way?). `gotchas` and `invariants` exist but have no provenance, no authoring event, no decay signal. Substring match fails completely for intent-based queries like "why can't we cache this" or "what broke last time we touched the batch pipeline." The system has no *institutional memory layer* — time-stamped, event-sourced observations retrievable by semantic intent rather than keyword coincidence.

### Core hypothesis
Highest-leverage change is not better search — it is adding a `memories` array to per-concept JSON where each entry carries `{text, kind, source_event, date, author}` with kind = `tried-and-dropped | anti-pattern | decision-rationale | performance-trap | open-question`. Pair this with a flat `docs/llm/SEARCH.txt` (one line per memory, slug-prefixed, ripgrep-able) and a second phase in doc-fetcher that greps SEARCH.txt after INDEX.json concept selection. No embeddings, no new agent type — just grep and structured JSON.

### Risks
- Authoring burden is the primary failure mode — memories must be written at moment of discovery by pipeline hooks, not deferred to a doc-update pass.
- Staleness without provenance poisons the well — undated memories become untrustworthy.
- 2 KB synthesis cap will be consumed by memories alone on hot concepts.
- SEARCH.txt fan-out at 500+ concepts.
- Human visibility — memories invisible to engineers unless synced to docs/human/.

### Plan implications
Schema change is small and backward-compatible. Authoring hooks (`/z-debug`, `/z-improve`, `/z-plan`) are the critical path — more work than the schema. SEARCH.txt is a derived artifact regenerated by doc-updater. doc-fetcher needs one extra Read for SEARCH.txt grep. 180-day decay policy automatable in doc-updater. Human tier sync via a `## Memories` section in `docs/human/<concept>.md`.

### What would change my mind
- If the real failure mode is "wrong concept selected, not missing memories," lookup investment wins.
- If grep proves vocabulary-unreliable for natural-language queries, embeddings become justified.
- If nobody reads `docs/human/`, single-tier memories are fine.
- If concept count stays below 30 with <5 memories each, enriched gotchas/invariants suffice with no schema change.

## Framing: Codex

### Framing
The current two-tier docs system solves *structural discovery* — "where does pattern X live?" But it doesn't capture *contextual intelligence* — "why didn't approach Y work?" or "watch out for time-zone bugs in bar boundaries." Orchestrators dispatch Explore when doc-fetcher returns no_match or partial, but Explore is expensive and sometimes misleading: it finds code without understanding *why* that code exists or what was tried first. Orchestrators also don't benefit from incident histories, abandoned experiments, or performance traps that live nowhere in the code. The audience is future planners re-solving the same problem, debuggers investigating failure modes, implementers avoiding deprecated patterns, and doc-fetcher itself (higher hit rate, faster dispatch).

### Core hypothesis
Memories live in LLM tier alongside `entry_points`, in a new `memories` array with provenance:

```json
"memories": [
  {
    "type": "anti_pattern | abandoned_path | incident | performance_trap | decision_rationale | open_question",
    "text": "<=200 chars narrative",
    "source": "incident:<slug> | spec:<plan-slug>/<run-id> | human_review:<name> | debug:<run-id>",
    "date": "YYYY-MM-DD",
    "tags": ["market-data", "missing-values", "backtest-correctness"]
  }
]
```

Lookup becomes a two-layer hybrid: (1) `docs/llm/MEMORIES-FLAT.md` — flat markdown listing all memories across concepts, ripgrep-able. doc-fetcher greps MEMORIES-FLAT.md alongside its INDEX.json scan; hits return concept slugs to fetch normally. (2) doc-fetcher still caps at 8 Reads — ripgrep is a free local pre-filter that returns only the best 3 concept slugs. Authoring: memories are written *during the lifetime of a concept* — `/z-debug` suggests an entry on root-cause; `/z-plan` logs why an approach was abandoned. Human-tier docs excerpt memories as a "Lessons learned" section extracted by doc-updater.

### Risks
- **Staleness and decay:** "Don't use pattern X" remains true for years, then becomes outdated. Mitigation: each memory has `date` and `confidence`; `/z-maintain-docs` flags memories older than 18 months for human review.
- **Authorship burden:** Subagents writing memories during retros require judgment, not mechanical extraction; wrong memories mislead future orchestrators.
- **Search false positives:** Ripgrep on raw memory text surfaces unrelated concepts (query "missing" hits both "missing market data" and "missing bounds check"). Mitigation: controlled tag taxonomy, require query+tag in the regex.
- **Two-tier sync failure:** Memories invisible to humans break trust — extraction into human tier is load-bearing.
- **Cost explosion:** Many ripgrep hits could trigger many JSON Reads, exceeding the 8-Read cap. Mitigation: rank and cap at 3.
- **Coverage gaps:** Not all gotchas are memorable; incident-driven ones are, subtle correctness invariants often aren't. System risks false confidence.

### Plan implications
- **doc-updater** gains memory-candidate detection from human prose and code comments.
- **`docs/llm/MEMORIES-FLAT.md`** auto-generated by `/z-maintain-docs` Phase 3, format `## <concept>\n[INCIDENT 2025-03-10] <text> (tags: ...)`.
- **doc-fetcher** gets `use_memories: true|false` (default true); ripgrep available as soft dependency, falls back to substring search if missing.
- **New `/z-suggest-memory` skill** invoked from `/z-debug` or `/z-plan` retros: prompts "What memory should future planners know?", user confirms/edits, written to concept JSON + MEMORIES-FLAT.md regenerated.
- `/z-init-docs` initializes empty MEMORIES-FLAT.md; `/z-maintain-docs` regenerates it every run.
- Ripgrep ~5ms typical; LLM tier grows ~500 bytes per concept; synthesis stays ≤2 KB (memories are summaries, not full narrative).

### What would change my mind
- **Toward human-tier-only memories:** if LLM-tier memories authored by subagents drift from human understanding within 3 months; if ripgrep surfaces wrong concepts >20% of the time.
- **Toward embeddings:** if reliable cheap embedding API available and latency <50ms; if substring/tag matching misses >50% of relevant concepts.
- **Toward "don't add memories":** if human reviewers already capture 80% of memory content in gotchas/entry_points descriptions today; if authorship cost exceeds the lookup benefit.
- **Toward dedicated docs-search agent:** if ripgrep latency becomes noticeable (>50ms); if ranking logic outgrows ripgrep.
- **Toward mandatory human-tier sync:** if telemetry shows humans never read or trust LLM-only content.

## Framing: Gemini

### Framing
The codebase itself is the source of truth for the *current state*, but it suffers from survivor bias — it only shows what worked, not what failed. Institutional memory (anti-patterns, abandoned paths, incident context) is currently lost between sessions or buried in git history. The goal is to persist this "dark matter" of software engineering in a way that is instantly accessible to an orchestrator *before* it begins planning or exploring, preventing repeated historical mistakes. The lookup mechanism must be zero-latency and highly deterministic to serve as a viable precursor to Explore.

### Core hypothesis
**Memories must be an append-only ledger, and search must be a flat, compiled text artifact.** Instead of allowing LLMs to mutate and potentially degrade "gotchas" through repeated summarization, memories should be an append-only array of timestamped, immutable events (e.g. `[{ "date": "...", "type": "abandoned-path", "content": "..." }]`) attached to a concept. To solve lookup without the operational complexity of vector databases, compile `INDEX.json` and all concept memories into a single highly structured flat text file (`SEARCH_INDEX.txt`). `doc-fetcher` is upgraded to use ripgrep over this flat file — semantic discovery becomes a blindingly fast regex-friendly filtering operation before any JSON is parsed.

### Risks
- **Context bloat:** append-only ledgers grow indefinitely; without eviction or compaction, doc-fetcher breaches its 2 KB synthesis cap on concepts with long histories.
- **Ripgrep noise:** flat text indexes are prone to false positives; a generic term yields dozens of hits across historical memories, confusing doc-fetcher about current architectural relevance.
- **"Two brains":** if rich memories only live in `docs/llm/`, humans never see them — divergence where AI knows mistakes to avoid that humans repeat.

### Plan implications
- **Schema update:** deprecate the simple `invariants` and `gotchas` strings. Introduce a `memories` array enforcing `date`, `provenance` (run-id, incident, or human-authored), `type` (`anti-pattern | decision | abandoned-path`), and `content`.
- **Index compilation:** new post-processing step in doc-updater flattens concept JSONs into `docs/llm/SEARCH_INDEX.txt`, formatted for grep (`[CONCEPT: <slug>] [TAGS: ...] [MEMORY: ...]`).
- **Agent modification:** rewrite doc-fetcher's retrieval contract — instead of reading INDEX.json and substring matching, it grep_searches the flat text index, extracts matched slugs, and *then* reads the targeted JSON files.
- **Authoring workflow:** hook `/z-debug` and `/z-improve` to automatically append memories to relevant concepts upon successful completion — the system organically learns from its own runtime operations.

### What would change my mind
- If empirical testing shows ripgrep against the compiled text file requires overly complex regexes to filter noise.
- If the sheer volume of "abandoned paths" makes keyword matching useless vs. the semantic accuracy of a cheap embedding search.
- If passing a massive INDEX.json directly to Haiku drops to near-zero cost — building a custom flat-file reverse index becomes unnecessary optimization.
