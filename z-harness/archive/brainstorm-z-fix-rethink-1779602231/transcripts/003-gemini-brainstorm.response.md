### 1. Framing

The current `z-debug` pipeline operates sequentially and relies heavily on LLM intuition ("guess and check"). It acts like a developer trying to remember what went wrong, rather than a scientist methodically eliminating variables. To achieve the reliability of Cursor's hypothesis-driven architecture, we must shift the framework from *verification* (trying to prove an idea is right) to strict *falsification* (proving an idea is wrong). By forcing the pipeline to maintain a written, persistent state of probabilities and using the multi-LLM setup adversarially, we can execute a "binary search" on the bug's root cause, eliminating entire classes of failure with single, targeted tests.

### 2. Core hypothesis

A formally tracked, Bayesian-style "Diagnostic Matrix" coupled with adversarial multi-LLM roles will drastically increase fix success rates. 

The mechanics:
*   **Divergent Generation:** Claude, Codex, and Gemini are explicitly prompted to generate *mutually exclusive* hypotheses (e.g., if Claude suspects data corruption, Gemini is forced to assume the data is perfect and hypothesize a UI rendering flaw). This yields a master list of 5-10 distinct hypotheses.
*   **Adversarial Falsification Design:** For the top hypotheses, the LLMs are not asked "how to fix this", but rather: *"What is the cheapest, read-only terminal command or script that will definitively DISPROVE this hypothesis?"* 
*   **The Artifact (`DEBUG_MATRIX.md`):** A physical file is maintained containing the tuple: `[Hypothesis] | [P(Truth)] | [Discriminating Test] | [Actual Result] | [Status: Active/Eliminated]`.
*   **Execution Loop:** Tests are batched. Read-only/non-mutating tests are executed in parallel. The matrix is updated with the real-world results. Eliminated hypotheses are struck out, and remaining probabilities are updated until only one root cause survives.

### 3. Risks

*   **Test Design Failure:** LLMs notoriously struggle to write truly discriminating, read-only tests. They may suggest abstract actions ("inspect the database") rather than executable scripts, stalling the loop.
*   **State Mutation & Pollution:** If a test inadvertently mutates state (e.g., running a test that writes to the DB), it cannot safely be run in parallel with others, and if teardown fails, it pollutes the entire testing environment, leading to false positives/negatives in subsequent hypotheses.
*   **Context Exhaustion:** Maintaining a detailed, running tally of 10 hypotheses, the bash scripts used to test them, and the resulting stdout/stderr across multiple turns could rapidly blow out the context window.
*   **Overhead for Trivial Bugs:** Applying a rigorous Bayesian matrix to a simple syntax error or obvious null pointer exception will severely degrade the user experience by taking 15 minutes to fix a 15-second bug.

### 4. Plan implications

*   **State Management:** Implement a literal `DEBUG_MATRIX.md` file writing/updating step in the pipeline. The CLI agent must parse this file to understand current state rather than relying entirely on conversation history.
*   **Consultant Role Expansion:** Update `codex-consultant` and `gemini-consultant` prompts to include two new modes: `generate-orthogonal` (to force divergence) and `design-falsifier` (to write negative tests).
*   **Testing Infrastructure:** Build a safe test-runner sub-phase that prefers ephemeral/dry-run executions to prevent state pollution.
*   **Triage Gate:** Introduce a "Fast Path" or "Complexity Classifier" early in the pipeline. If the initial reproduction immediately isolates the bug to a single line with 95% confidence, bypass the matrix entirely and jump to the fix phase.

### 5. What would change my mind

*   If empirical runs show that the Multi-LLM generation consistently produces highly overlapping hypotheses, proving that forcing divergence is artificial and yields low-quality, hallucinatory "filler" hypotheses.
*   If the LLMs are structurally incapable of writing zero-side-effect test scripts, resulting in the test runner breaking the local workspace.
*   If telemetry reveals that the very first hypothesis generated by the primary agent in the current `z-debug` is already the correct root cause >80% of the time, making the matrix and falsification loop an expensive solution in search of a problem.
