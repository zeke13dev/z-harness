## Overview

The skills concept covers the operational playbooks behind z-harness slash commands. Each `skills/<name>/SKILL.md` file (and several `commands/*.md` files that define full pipelines) specifies a command's phases, telemetry, user gates, subagent dispatches, output artifacts, and hard safety rules. These files are the practical source of truth for how planning, terrain mapping, deep research synthesis, debugging, implementation orchestration, test-case planning, final review, docs maintenance, memory authoring, statistics reporting, self-update, bulk quality uplift, targeted component auditing, fast-path bug fixing, plan-correctness auditing, plan-style auditing, skill-file patching, and active-run inspection should run.

The skill family shares a route-policy model: planning and execution skills collect deterministic signals, call the advisory `planning-router` only when signals conflict, write `route-decision.md`, emit `plan_route_decision`, present an AskUser handoff gate, and stop rather than auto-running the next command. Skills reference stable provider-registry agent roles (`consultant-primary`, `consultant-secondary`, `reviewer`) and shared scripts for path resolution and logging. Skills that produce PushNotifications gate every call through `config.py should-notify --event <type>` (returns `yes`/`no`); notification policy and other runtime knobs are documented in `docs/human/config.md`. Skills with an explicit Setup block run `eval "$(config.py export-env)"` early to populate all `Z_HARNESS_*` env vars from config — `z-do` and `z-plan` are the two current adopters. Four skills have auto memory-review phases: `z-implement-all` (Phase 9), `z-review-all` (Phase 7), `z-debug` (Phase 10 — shipped branch only), and `z-suggest-memory` (sole memory authoring path, supports `--from-candidate-json` for review-agent output). All memory-review phases share a common pattern: `run-memory-review.sh` gates dispatch, the skip path emits `memory_review_terminal` via the helper, the ready path dispatches a `review-agent` subagent, and the terminal `memory_review_terminal` event (with `state: needs_user` or `ran_empty`) is emitted once per invocation. Push-notify for broken-context skip reasons uses a per-session dedup file (`.notify-dedup-session`) to suppress duplicate notifications. Three skills resolve the kernel path exactly once at Setup via `bash scripts/resolve-kernel.sh`; when `KERNEL_PATH` is non-empty, it is injected as a `kernel_path:` line into every behavioral-agent dispatch (consultant, implementer, reviewer) in that run — `z-debug`, `z-plan`, and `z-implement-all` are the current adopters.

Most execution skills now carry a **registry lifecycle integration** (Phase 0.0): immediately after slug/base discovery, each skill registers its run in the shared `active-plan-registry.py` with `--run-id`, `--slug`, `--command`, `--phase`, and `--session`. A graduated failure policy applies — `REG_RC == 3` (register failed, no record written) triggers an interactive proceed/abort question (or unattended proceed with `Z_HARNESS_STRICT_OVERLAP=1` halting); any other nonzero is treated the same. On `REG_RC == 0`, a scope-seeding `scope-extractor` (Haiku) subagent seeds file scope into the registry for overlap detection, then an overlap scan runs with `active-plan-registry.py overlaps`: exit-0 (no overlap) proceeds silently; exit-10 (advisory) offers proceed/wait/abort; exit-20 (blocking, strict-mode only with explicit×explicit path match) halts unconditionally. The FINALIZE_STATUS rule governs the entire lifecycle: any run-ending halt after a record exists sets `FINALIZE_STATUS=aborted` and calls `deregister --status aborted`; normal completion calls `deregister --status complete`; compaction-pause exits do not deregister. Skills heartbeat the registry at each task-dispatch boundary (best-effort, `|| true`). The `z-where` command is a read-only diagnostic that prints the resolved base/repo-id header and a live table of all active plans from the registry, optionally checking path-overlap for a specific run-id — no writes, no LLM calls, no subagent dispatch.

Six skills carry the slug-confirm preference resolver retrofit: `z-plan`, `z-fix`, `z-debug`, `z-brainstorm`, `z-map`, and `z-plan-light`. The pattern is: hard unconditional slug-dir collision check first, then a soft non-obvious-slug confirmation gate via `python3 scripts/config.py resolve-question workflow.slug_confirm`. The resolver returns `skip` (silently accept, emit `askuser_skipped`), `prefill` (pre-select in AskUserQuestion with a preference label), `ask` (normal prompt; if `source == "conflict"`, surface the conflict details and offer a one-shot follow-up to record the user's answer as the new preference), or `halt` (emit a skill-specific halt event — e.g. `brainstorm_halt`, `debug_halt`, `light_halt`, `map_halt` — and exit cleanly without invoking `AskUserQuestion`; applies when `Z_HARNESS_NO_ASK=halt` is active and the resolver's no-ask gate returns `halt`). The `halt` result is a hard exit path: no AskUserQuestion is called, the run emits its skill-specific halt event, and control returns to the user. `config.py` also emits `askuser_resolved` events each time a question is resolved. `z-stats` Phase 4c reads these `askuser_resolved` events to show preference resolution statistics and conflict rate across the last 10 runs. `z-suggest-memory` gained a new `--kind routing-preference` mode that writes structured routing-preference memory entries to `docs/llm/workflow.json` (global) or `docs/llm/workflow-<project-slug>.json` (project scope), bypassing normal interactive collection. Its Phase 3a also gained a routing-flavored text detection gate: if candidate text matches `(always|usually|every time).*(after|before|when)`, the skill offers three branches — write to config.toml (yes-config), write as a routing-preference memory, or continue as a lesson-learned memory. `z-review-all` Phase 3.7 now runs a two-stage gate: a no-ask check (`config.py check-no-ask --question-id workflow.review_all_proceed`) fires first; if it returns `halt`, Phase 3.7 writes a partial `.review_state.json` (with `halted: true, halt_reason: no_ask_blocked`) and exits without calling AskUserQuestion. The Pre-Phase 0 resume check recognizes this halted-state file, emits `review_resume_from_halt`, deletes the file, and proceeds to a full Phase 0 re-run.

Four skills now carry **persona behavior** that augments (never replaces) the neutral cross-LLM consult. These are all controlled by config knobs and degrade gracefully — when a knob is off or the persona pool underflows, the dispatch is byte-identical to the pre-persona baseline. `z-brainstorm` Phase 2a draws up to 3 distinct `ideator` personas (controlled by `brainstorm.personas` knob, default ON) from `resolve-persona.py random-distinct-for-role ideator --count=3` and prepends one persona body to each of the three vendor-diverse ideators (Claude/Codex/Gemini); `persona_bound` events are emitted per bound ideator; the drawn persona IDs are recorded in BRAINSTORM.md `ideator_personas` frontmatter. `z-debug` Phases 3a and 3b use a fixed 5-panel of consultants (agy/gemini, cursor@claude-4.6-sonnet, cursor@grok-4.3, cursor@composer-2.5, codex-cli) when `experiment.persona_rotation == "true"` (default); when `personas.critique_panel == "true"` as well, the skill draws 5 distinct `consultant` personas for each panel arm in Phase 3a and reuses the same draw in Phase 3b, emitting `persona_bound` with `selection_source=random_role_pool_distinct` per arm (or `selection_source=fixed_panel` for vanilla slots); when `experiment.persona_rotation == "false"`, the skill falls back to the standard 2-consultant dispatch. `z-plan` Phases 3 and 7 likewise use the fixed 5-panel when `experiment.persona_rotation == "true"` and draw independent sets of 5 distinct `consultant` personas (Phase 3 draw does not carry over to Phase 7); `personas.critique_panel == "true"` gates the actual persona prefix application, same graceful-underflow semantics as `z-debug`. `z-plan-light` Phase 3 gains a measured advisory arm controlled by `personas.consult_eval` (default OFF): when true, one `consultant` persona is drawn and a third arm is dispatched in parallel with the two neutral arms; its output is captured as `persona_advisory_recommendation` telemetry and is never folded into the Phase 4 synthesis (the neutral-authority contract is load-bearing); the advisory arm's `persona_bound` event carries `selection_source=random_role_pool` (not `_distinct`). `z-plan-light` Phase 8 gains a parallel advisory eval-reviewer arm controlled by `personas.review_eval` (default ON): one `reviewer` persona is drawn using `random-for-role reviewer` (`selection_source=random_role_pool`) and runs in parallel with the base codex reviewer; the base reviewer remains the sole authoritative gate; the advisory arm's verdict is logged only.

## How it interacts with others

- `commands` — Commands are the user-facing surfaces that mirror or invoke these skill workflows. Route-policy changes must stay aligned between command markdown and skill markdown. Several commands (`z-audit.md`, `z-audit-plan-style.md`, `z-fix.md`, `z-skill-fix.md`) define their pipelines directly in `commands/` without a corresponding `SKILL.md` re-entry alias.
- `agents` — Skills define when to dispatch `doc-fetcher`, `doc-updater`, `planning-router`, `implementer`, `reviewer`, `consultant-primary`, `consultant-secondary`, `review-agent`, `complexity-classifier`, `auditor`, `bisect-isolator`, `plan-style-reviewer`, `scope-probe`, `scope-extractor`, `cluster-planner`, `axiom-extractor`, and other subagents, plus the exact prompt contracts those agents receive. Persona behavior introduces `resolve-persona.py` as the draw mechanism for `ideator` and `consultant` roles, with `persona_prompt.py` formatting the prefix.
- `scripts` — Skills rely on `plan-path.sh`, `log-event.sh`, `log-phase.sh`, `version.sh`, `regenerate-memories-flat.py`, `run-memory-review.sh`, `active-plan-registry.py`, `config.py`, `resolve-persona.py`, and `resolve-kernel.sh` for path resolution, telemetry, version stamping, memory flat-file sync, memory-review orchestration, active-plan registration/overlap detection, config-env export, persona pool draws, and kernel-path resolution.
- `active-plan-registry` — The registry (`scripts/active-plan-registry.py`) is the shared coordination layer that all execution skills register with at run start, heartbeat during task dispatch, and deregister at run end. `z-where` and `z-stats` read from it; execution skills write to it.
- `multi-ide-exports` — Export pipelines consume these skill files to generate Cursor rules, Codex prompts/skills, and Antigravity skills/workflows, so source skill edits must propagate through exported surfaces.
- `providers-registry` — Skills refer to stable agent roles (`consultant-primary`, `consultant-secondary`, `reviewer`) while provider resolution happens behind those roles. Persona behavior adds a draw layer on top of stable roles — the persona prefix is prepended to the prompt, but the underlying subagent type (and thus provider resolution) is unchanged.

## Edge cases / gotchas

- Route handoffs are not command chaining. Skills write a route decision, emit telemetry, ask the user, and stop after presenting the next command.
- The `planning-router` is advisory only. Deterministic thresholds win, malformed output falls back to deterministic routing or AskUser, and loop-prevention blocks ping-pong route chains capped at two entries.
- `/z-audit-plan` is only valid when plan artifacts exist. If none are found, it writes a no-plan route decision toward `/z-plan` instead of fabricating an audit.
- `/z-do` may not route directly to `/z-plan-split`; larger work routes through `/z-plan`, `/z-plan-light`, `/z-research`, `/z-brainstorm`, `/z-fix`, or `/z-debug` based on signals. Doc-fetcher dispatch in `/z-do` is skipped entirely when `$Z_HARNESS_DOCS_ALWAYS_APPLY=never` (set via config knob).
- `/z-plan-split` keeps `cluster_id` (e.g. `C1`, `C2`) separate from `cluster_slug` (the path segment). Swapping them breaks telemetry and on-disk layout. The `--clusters` flag supplies names only; scopes must still be derived per cluster.
- `/z-implement-all --tasks=<path>` bypasses normal slug/tree discovery and derives `$BASE` from the task file's parent directory; this is how promoted `REVIEW-TASKS.md` or `MR-REVIEW.md` queues are consumed.
- `/z-implement-next` is single-shot — no auto-retry on review failure. For retry, manually set the task stamp to `**Complexity:** high` and re-invoke, or use `/z-implement-all` which handles the retry loop.
- `/z-implement-next` Phase 0.0 registration runs AFTER Phase 0.2 slug-discovery (which binds `$BASE`) and BEFORE Phase 0.1 lock-check. The execution order is 0.2 → 0.0 → 0.1, not the document order.
- Registry registration failure (`REG_RC == 3`) means no record was written — do NOT call `deregister` on this path; deregistering a non-existent record is misleading. On any other run-ending halt AFTER a successful register, FINALIZE_STATUS=aborted + deregister is mandatory.
- Compaction-pause exits (condition 3 in `/z-implement-all`) are pauses, not aborts — do NOT deregister on a pause. The next invocation re-registers idempotently.
- `Z_HARNESS_STRICT_OVERLAP=1` adds a single hard gate: `OVL_RC == 20` (blocking overlap with explicit×explicit path match) halts unconditionally. Without this flag, overlap is always advisory.
- `memories[]` are never authored by doc-updater. `/z-suggest-memory` is the only supported mutation path, and both stale-memory deletes and memory edits use atomic JSON writes.
- Phase 9 (`z-implement-all`) and Phase 7 (`z-review-all`) are soft phases: all failure paths are silent skips — no halt, no retry. They call `run-memory-review.sh` to gate whether a review-agent dispatch is warranted. Phase 10 (`z-debug`) follows the same pattern but only runs on the `status: shipped` branch — abandoned debug sessions emit no memory-review telemetry.
- `--from-candidate-json` in `z-suggest-memory` bypasses Phases 3a–3f; the candidate object must have `type` and `text` fields or the skill returns `STATUS: bad_input`. Pass `-` as path to read from stdin.
- The slug-confirm preference resolver in `z-brainstorm`, `z-map`, `z-plan-light`, `z-debug`, and `z-fix` (Setup) now has four result values: `skip`, `prefill`, `ask`, and `halt`. The `halt` result fires when `Z_HARNESS_NO_ASK=halt` is active and the `check-no-ask` gate returns `halt` for the slug-confirm question. Each skill emits its own halt event (`brainstorm_halt`, `debug_halt`, `light_halt`, `map_halt`) and exits without invoking AskUserQuestion. The hard unconditional slug-dir collision check runs before the resolver and is never bypassed by resolver outcome.
- `/z-review-all` Phase 3.7 compaction breakpoint now runs a two-stage gate: (1) `config.py check-no-ask --question-id workflow.review_all_proceed` fires first — if it returns `halt`, Phase 3.7 writes a partial `.review_state.json` with `halted: true, halt_reason: no_ask_blocked` and exits without calling AskUserQuestion; (2) if the no-ask gate returns `proceed`, the full `resolve-question workflow.review_all_proceed` resolver runs for skip/prefill/ask. On the next `/z-review-all` invocation after a `halt`, the Pre-Phase 0 resume check detects the halted-state file, emits `review_resume_from_halt`, deletes the file, and runs a full Phase 0 re-run.
- Persona behavior across all four skills degrades gracefully — when a config knob is off or `resolve-persona.py` returns an empty/underflow array, each affected arm's prompt is byte-identical to the pre-persona baseline. No arm is skipped; only the prefix is absent.
- `z-brainstorm` ideator personas are drawn once per Phase 2a using `brainstorm.personas` knob. The `ideator_personas` map in BRAINSTORM.md frontmatter records `"<none>"` for any slot that underflowed. When the knob is OFF, the map is omitted from frontmatter and no `persona_bound` events are emitted.
- `z-debug` and `z-plan` persona draws are per-phase: Phase 3a draw ≠ Phase 3b draw is false (3b reuses Phase 3a draw); Phase 3 draw ≠ Phase 7 draw in `z-plan` (independent draws). For `z-debug` Phases 3a and 3b the same personas are reused (same `persona_id` and `draw_id` in `persona_bound` events).
- `z-plan-light` Phase 3 advisory arm outputs `persona_advisory_recommendation` telemetry events. The neutral-authority contract is mechanical: even if the persona advisory arm recommends a different option than both neutral arms, Phase 4 synthesizes from the neutral arms only. No prose path in Phase 4 may read the advisory arm's output into the final recommendation.
- `z-plan-light` Phase 8 advisory eval-reviewer arm is defined by a shared snippet in `commands/z-implement-all.md` (HTML anchor `<!-- ADVISORY-EVAL-REVIEWER -->`). The skill references this canonical snippet rather than copying bash inline. The base codex reviewer's blockers/majors counts remain the sole driver of re-edit/halt logic.
- `z-plan-light` advisory arm (`personas.consult_eval`) emits `persona_bound` with `selection_source=random_role_pool` (single draw, not `random_role_pool_distinct`). Same applies to the Phase 8 advisory eval-reviewer draw.
- `z-suggest-memory --kind routing-preference` writes to `docs/llm/workflow.json` (global scope) or `docs/llm/workflow-<project-slug>.json` (project scope). If the target file does not exist, it is created as a minimal stub and registered in INDEX.json. Mutually exclusive with `--edit`, `--delete`, and `--from-candidate-json`.
- Adding a tag alias records TAGS.txt only; memory tags collapse on a later run when doc-updater's step 3.5 reads the updated TAGS.txt.
- MEMORIES-FLAT.md regen is mandatory after doc writes or memory mutations.
- `/z-debug` Phase 2.5 bisect is a conditional fast-path, not a required phase. It fires only when the bug is a regression with a known-good baseline and a scriptable repro. `refused`, `failed`, and `bisect_unusable` returns all fall through to Phase 3a unchanged — bisect never blocks the pipeline.
- `/z-debug` auto-bail thresholds no longer include `>5 files` as a trigger; only cross-module impact, architectural change, or new public surface trigger escalation. The hard cycle cap is 5 (halt when cycle 6 would be needed); soft warning fires at cycle 3.
- `/z-fix` Phase 0 is non-skippable even if the user passed an argument. A symptom description alone is not a hypothesis — if the user cannot name a cause, the command exits with a `/z-debug` recommendation.
- Phase 4b in `z-stats` reads both `review_agent_call` events and `memory_review_terminal` events from metrics.jsonl, with a back-compat mapping from old `phase_end` shape; it is read-only and adds no writes.
- Phase 4c in `z-stats` reads `askuser_resolved` events to produce a preference resolutions summary (by result, source, question_id, and conflict rate). It is read-only. If no events are found, it prints a "none found" note and skips the conflict-rate line.
- `memory_review_terminal` is the canonical terminal event for all memory-review paths. It is emitted by `run-memory-review.sh` for all skip states, and by the orchestrating skill for `ran_empty` and `needs_user` states. `review_agent_failed` and `review_agent_malformed` are orthogonal failure-class events — they do NOT emit `memory_review_terminal`.
- `config.py export-env` populates all `Z_HARNESS_*` env vars from the project config at startup (currently used in `z-do` Setup step 6 and `z-plan` Setup step 4a). Skills that do not yet call `export-env` must not assume `Z_HARNESS_NOTIFY` is set; they reference the `docs/human/config.md` pointer and use `Z_HARNESS_NOTIFY_LEVEL` with a default fallback.
- `z-maintain-docs` default mode applies clean concepts without prompting; pass `--dry-run` to preview without writing. Only `flagged` concepts — `memories_lost` mismatch or (under `--audit`) rejected/needs-review verdict — require per-concept `AskUserQuestion` before writing. `deferred` (not_enough_info) concepts are never written.
- `z-plan` Phase 9 push-notify lists `/z-audit-plan-style` alongside `/z-audit-plan` as a separate recommendation. The `AskUserQuestion` four-option cap bundles them under the `Audit the plan (recommended)` label but the description points to both. The user's answer is logged as a `next_step_choice` event; the command is never auto-dispatched.
- Kernel path resolution (`resolve-kernel.sh`) happens once per run at Setup in `z-debug`, `z-plan`, and `z-implement-all`. When `KERNEL_PATH` is non-empty the path string is injected as `kernel_path: <path>` into every behavioral-agent prompt in that run; when empty, the line is omitted entirely.
- `/z-debug` Phase 10 shipped branch: if `run-memory-review.sh` returns a line starting with `AXIOM_READY`, an `axiom-extractor` subagent is dispatched in parallel with the `review-agent`. The axiom-extractor proposes only — no auto-approve; orchestrators do not block on its return.

## Examples

- To understand a route bailout from light mode, read `skills/z-plan-light/SKILL.md` Plan Route Check and Phase 1. The artifact to inspect is the run's `route-decision.md`.
- To debug why tree-rooted implementation refused to start, read `skills/z-implement-all/SKILL.md` Setup 2b for MANIFEST, SHARED-CONCERNS, partial-tree, and ack validation gates.
- To add a durable lesson after a debug or retro run, use `/z-suggest-memory`; do not edit `memories[]` directly and do not ask doc-updater to invent memory entries.
- To pipe a review-agent candidate directly into memory, run `/z-suggest-memory --concept <slug> --from-candidate-json <path> --source "incident:<run-id>"`.
- To record a routing preference (e.g. always confirm slug), run `/z-suggest-memory --kind routing-preference --question-id workflow.slug_confirm --value prefill --strength strong --scope global`.
- To see how many memory candidates the last implement-all run surfaced and how many were accepted, run `/z-stats` and check the Phase 4b output — it shows `review_agent_call` counts and `memory_review_terminal` state aggregations for the last 10 runs across all parent commands.
- To see how often slug-confirm prompts were skipped or prefilled by a stored preference, run `/z-stats` and check the Phase 4c "Preference resolutions" section — it shows counts by result, source, question_id, and conflict rate.
- To resume a `/z-review-all` run that was interrupted after building the cumulative diff, re-invoke `/z-review-all`; if `.review_state.json` is valid and HEAD is unchanged, Phases 0–3.5 are skipped automatically.
- To consume a promoted REVIEW-TASKS.md queue without full plan discovery, run `/z-implement-all --tasks=z-harness/<slug>/REVIEW-TASKS.md`.
- To implement one task at a time (manual pacing), use `/z-implement-next`; it does not auto-advance and keeps each task in a fresh context per task.
- To plan semantic test cases before implementation, use `/z-test` after `/z-plan`; the TESTS.md it produces is consumed by `/z-implement-all` automatically.
- To run a full-codebase quality pass, use `/z-uplift`; for a single component only, use `/z-audit <target>`; for branch-diff review before merging, use `/z-mr-review`.
- To update the z-harness plugin itself, run `/z-update`; it detects symlink vs tarball and picks the safe update path automatically.
- To fix a bug when you already have a hypothesis, use `/z-fix`; if the root cause is unknown, use `/z-debug` instead (Phase 0 of both commands routes appropriately).
- To inspect the notification policy or change it project-wide, read `docs/human/config.md`; the `notify.level` knob controls which events fire PushNotification calls.
- To see what plans are currently running (or were abandoned without cleanup), run `/z-where`; it shows all active registry records with age and staleness indicators, no LLM calls.
- To disable ideator personas for a brainstorm run without changing config, set `brainstorm.personas = false` in `.z-harness/config.toml`; the dispatch becomes byte-identical to the pre-persona baseline.
- To disable the 5-panel consultant expansion for a debug or plan run, set `experiment.persona_rotation = false` in `.z-harness/config.toml`; the skill falls back to the standard 2-consultant dispatch.
- To preview which docs are stale before writing, run `/z-maintain-docs --dry-run`; to apply all stale updates directly (the default), run `/z-maintain-docs`.
