## Overview

The `commands` concept covers the slash-command specifications that drive z-harness workflows. Each command lives as a Markdown procedure under `commands/` and defines a user-facing orchestration path: planning, research, debugging, fixing, implementation, review, docs maintenance, memory authoring, audits, tests, stats, skill repair, plugin updates, bulk codebase uplift, style-guide authoring, provider discovery, cross-IDE export, unattended overnight pipeline execution, attended middle-gear chain execution, follow-up queue management, handoff/resume, session evaluation, context-budget analysis, code debt scanning, axiom lifecycle management, persona inspection, configuration setup, and diagnostics.

The command surface is organized around explicit routing, durable artifacts, and a closed-loop memory layer. Commands that send notifications or apply docs call `scripts/config.py export-env` during Setup to resolve `Z_HARNESS_NOTIFY_LEVEL`, `Z_HARNESS_DOCS_ALWAYS_APPLY`, and related knobs from the layered TOML config (see `docs/human/config.md`). Notification guards are expressed as `[ "$(scripts/config.py should-notify --event <type>)" = yes ]` wrappers rather than raw env-var checks. Planning-family commands collect deterministic route signals, consult `planning-router` only when signals conflict, write `route-decision.md`, emit `plan_route_decision`, and ask the user before switching. `/z-plan` step 9c runs a consolidated freshness gate covering docs-staleness, RESEARCH.md/MAP.md citation freshness in a single `AskUserQuestion`; a Proceed-with-all-stale choice emits `precontext_freshness_acknowledged` and sets `to_command: null` in `plan_route_decision`. Review-family commands preserve evidence separately from promotion artifacts and route actionable findings through `/z-execute --tasks`. Both `/z-execute` (Phase 9) and `/z-review-all` (Phase 7) close the loop by running `run-memory-review.sh` after each plan completes, dispatching a `review-agent` to surface memory candidates, persisting them as JSONL, and notifying the user to review with `/z-suggest-memory --from-candidate-json`; Phase 9 emits `memory_review_complete` — there is no in-phase AskUserQuestion loop. `/z-debug` (Phase 10) also runs `run-memory-review.sh` after a shipped fix and uses a 5-line stdout contract; Phase 10 does have a sequential AskUser loop capped at 3 candidates and its terminal event is `memory_review_terminal`. The abandoned branch skips memory review entirely.

**Active-plan registry lifecycle:** Run-creating commands (`/z-plan`, `/z-execute`, `/z-do`, `/z-debug`, `/z-audit`, `/z-plan-split`) all participate in a shared active-plan registry via `scripts/active-plan-registry.py`. Each run registers itself (immediately after slug discovery and structural validation), seeds its file scope via a `scope-extractor` subagent, runs an overlap scan against concurrent sessions, sends periodic heartbeats at phase boundaries, and deregisters on completion or abort. The FINALIZE_STATUS rule governs the lifecycle: after a successful register (`REG_RC == 0`), any run-ending halt sets `FINALIZE_STATUS=aborted` and calls `deregister --status aborted` before exiting; if register failed, the command never calls deregister. Overlap is advisory by design (lockless); strict mode (`Z_HARNESS_STRICT_OVERLAP=1`) adds a single hard gate on exact path collisions. `/z-stats` Phase 0b prints the resolved base, repo-id, and active-plan count unconditionally. `/z-where` is a read-only diagnostic command (no LLM calls, no subagent dispatch) that prints the resolved base + repo-id and a table of all active plans from the registry with optional overlap detection. `/z-context-budget` and `/z-evaluate` register with the registry in advisory-only mode even though they are read-only analysis commands.

**Artifact Scout preflight lifecycle:** Duplicate-work/collision scouting is split into deterministic inventory plus an optional classifier. `scripts/artifact-scout-inventory.py` writes `$BASE/archive/$RUN/artifact-scout-inventory.json` and emits `artifact_scout_inventory_complete`; the tool-less `artifact-scout` Haiku agent consumes only inline compact JSON and, when run, archives its raw response as `$BASE/archive/$RUN/artifact-scout.md`. Prod-surface direct scout hooks are `/z-plan`, `/z-uplift`, `/z-plan-split`, `/z-brainstorm`, `/z-audit`, `/z-debug`, `/z-audit-plan`, and `/z-audit-plan-style`. Dev-only experimental commands may add the same scout lifecycle when those commands are present in a development install. Attended wrappers do not scout independently and only pass through child scout artifacts when their wrapped child command produced them.

Hard-gated prod-surface scout hooks (`/z-plan`, `/z-uplift`, and `/z-plan-split`) follow the same split even when the hard gate is later in the flow: deterministic inventory may run before the gate, but the optional `artifact-scout` Agent classifier is post-gate only. Dev-only hard-gated commands follow this invariant when present in a development install. The invariant is no pre-gate `Agent()` dispatch for scout classification or other expensive reasoning.

**Artifact Scout route boundary:** Scout output is advisory unless it explicitly returns a route recommendation whose JSON has `route_chain_effect: "write_route_decision"`. Warning-only results (`STATUS: warned`, `allowed_action: warning_only`, or `route_chain_effect: "none"`) are displayed/logged but never write `route-decision.md`, never emit `artifact_scout_route`, and never advance `route_chain`. Route-capable scout findings share the existing `route-decision.md` / `plan_route_decision` boundary: write the artifact, ask the user to switch/continue/abandon, and never auto-execute the next command.

**Source-status semantics:** The inventory records source health for `plans`, `archives`, `registry`, and `worktrees`. `ok` means evidence was collected; `missing` means that source was absent; `partial`, `corrupt`, `unavailable`, and `truncated` are treated as unknown evidence, not proof of absence. The classifier reports such sources in `unknown_sources`, caps confidence, and may warn with `unknown_sources_present`, `inventory_partial`, or `inventory_truncated`. LLM concept JSON (`docs/llm/INDEX.json` and `docs/llm/*.json`) is generated material and remains for a later `/z-maintain-docs` refresh; do not hand-edit it for this lifecycle.

`missing` is a source-health fact, not a negative duplicate-work proof: the classifier must not treat a missing archive/registry/worktree source as evidence that no matching artifact or peer exists.

**Persona rotation and personas-everywhere (experiment, on by default):** When `experiment.persona_rotation=true`, `/z-execute` calls `resolve-persona.py random-for-role implementer` before each task attempt; every `experiment.control_every_n`-th attempt uses `forced-control` (boring-anchor). The draw result is persisted to `$BASE/archive/tasks/<task-id>/persona-draw.json`; resumes reuse the same draw, retries respect the `personas.implementer_retry` knob (`"same"` default: same persona across all cycles; `"new"`: fresh draw to per-cycle sidecar `persona-draw-v<CYCLE>.json`). It dispatches a dual reviewer (base codex + one advisory random-arm) when `personas.review_eval` is also on (default ON). `/z-plan` (Phases 3 and 7) and `/z-debug` (Phases 3a, 3b) use a fixed 5-panel consult when `experiment.persona_rotation=true`; the `personas.critique_panel` sub-knob governs whether each arm additionally draws a distinct `consultant` persona prefix — Phases 3 and 7 draw independently; Phase 7 (fix-consult) in `/z-debug` uses the fixed 5-panel but emits `selection_source=fixed_panel` for all arms (no persona prefix draw). `/z-brainstorm` Phase 2a draws 3 distinct `ideator` personas when `brainstorm.personas` is ON (default ON). `/z-audit` Phase 2a draws up to 4 distinct `audit_persona` personas when `personas.audit` is ON (default ON). `/z-fix`, `/z-do`, and `/z-execute` all gate an advisory eval-reviewer at their Codex review gates via `personas.review_eval` (default ON); the canonical "Advisory eval-reviewer (shared snippet)" lives in `skills/z-execute/SKILL.md`. All rotation behavior is a no-op when the governing knob is off.

**Follow-up sink and Phase 0 consumer check:** `/z-review-all` Phase 3.7.5 routes non-halting review findings into the project follow-up sink via `scripts/sink-add.sh` and `scripts/parse-followups-block.py`. `/z-execute` and `/z-review-all` all run a Phase 0 concurrent follow-up consumer check before any task dispatch. The check reads `z-harness/followups/index.view.json`, counts entries with `status == "running"` using a dict-safe parse (`entries` is a dict keyed by entry-id, not a list), and halts with `implement_halted_followup_running` (implement commands) or `review_halted_followup_running` (review command) if any are running. The six `/z-followup-*` commands form the consumer interface for the follow-up sink. All six carry a nest guard that blocks invocation from within a running follow-up entry's recommended command (`Z_HARNESS_FOLLOWUP_CALLER_DEPTH >= 1`).

**Scope probe (v1a) and brainstorm conversational tail:** `/z-audit` and `/z-brainstorm` run a Haiku `scope-probe` subagent as Phase 0 to classify the topic as LIGHT / MEDIUM / HEAVY. Both commands additionally have a Phase 0 fast-path: when the target is a single file path, Phase 0 is skipped and the target is auto-classified as LIGHT (emitting `scope_probe_skipped_fast_path`). `/z-brainstorm` Phase 0 adds two steps BEFORE scope-probe: (1) a sharpen-vs-skip gate that auto-invokes `/z-sharpen` inline when the topic is vague (producing `GRILL.md` as seed framing; emits `sharpen_gate`), and (2) an NL count parse that extracts the desired ideator count N from the topic text (default 3; emits `count_parsed`). When N > 3 (wide mode): a conversational cost gate (end-turn, not a popup) precedes dispatch; overflow waves use anti-seeded divergent prompts and distinct personas; `ideator-clusterer` (Haiku) collapses N framings into K distinct directions. D2 invariant: wide N > 3 with HEAVY scope suppresses HEAVY fan-out (treats as MEDIUM). Phase 3 produces a ranked prose briefing and ends the turn — the orchestrator MUST NOT auto-decide. Phase 4 LIGHT/MEDIUM is a conversational discussion loop (ask/combine/re-spin cap 3/lock-in/abandon); `synthesized` is the default `chosen_framing` for discussion-born hybrids. Phase 4 HEAVY presents the `(chunk × framing)` ranked-pair briefing inline (end-turn, not a popup).

**Amendment-brief overhaul in audit/review:** `/z-review-all` Phase 6.5 unconditionally auto-amends every `amendment_proposal` (spec_gap class) via `/z-amend --skip-user-gate` (blocker/major/minor all auto-amend; implementation_drift stays as candidate fixup tasks). Phase 6.6 renders a unified amendment brief via `scripts/amendment-brief.py` (corrections = Phase 6.5 spec_gaps, approach_concerns = premise_failure escalations); writes `amendment-brief.md` to archive; skipped when both lists are empty. `/z-audit-plan` Phase 5 default (source==none) is `auto_split`: in INTENT-mode, all spec_gap findings batch into ONE `/z-amend` call (single contract re-freeze); legacy-mode is per-finding; premise_failure rendered via `amendment-brief.py` as conversational prose. `force_ask` fires only when `amend-gate-decision.py` returns `force_ask` (explicit config/memory ask/prefill preference). `workflow.audit_to_amend` is SOURCE-KEYED: stored value alone does not determine behavior; resolver source is the discriminator.

**Attended middle-gear chain (`/z-attend`):** A new middle-gear command between `/z-overnight` (fully unattended) and manual one-command-at-a-time. Auto-advances through a command chain (default preset `attend-full` = `plan,audit,test,implement-all,review-all`), halts and asks inline only on four halt categories (`decision`, `risk`, `shortcut`, `archiving`), auto-proceeds `mechanical_proceed` gates with `skill_default`, and yields for a real user `/clear` at declared yield_after boundaries. Resume validates a hardened `handoff.json` protocol-1.1 predicate: HEAD SHA mismatch = HARD HALT, phase/cursor disagree = HARD HALT, session_id unchanged = WARN. **Invariant 1 (fail-safe):** any gate with no explicit halt category resolves to `ask`, never `mechanical_proceed`. Gate policy lives in `z-attend.md`; sequencing/state mechanics live in `chain-runner.sh` (policy separation Invariant 2).

**Axiom lifecycle commands:** Five commands manage the axiom store. `/z-axiom-scan` mines candidate axioms from interaction history via the `axiom-extractor` agent; `--historical` triggers a full `metrics.jsonl` scan; it proposes only, never auto-approves. `/z-axiom-list` renders a filtered read-only table from the store. `/z-axiom-approve` shows the candidate, evidence, and falsifiability state; requires explicit user confirmation before approving; triggers synchronous KERNEL.md regeneration on approval. `/z-axiom-reject` tombstones a candidate or approved axiom. `/z-axiom-edit` edits a field and re-validates the graph + regenerates the kernel for approved records.

**Resolver hooks and elevation proposer:** Several commands integrate `scripts/config.py resolve-question <question_id>` to consult stored preferences before presenting `AskUserQuestion` gates. The resolver returns `{result: skip|prefill|ask, default, source}` and the command branches accordingly. After major user-gate decisions, `/z-audit-plan` (Phase 9), `/z-audit-plan-style` (Phase 9), and `/z-amend` (Phase 9) run an Elevation Proposer via `scripts/propose-prefs.py --check <cmd>`. Seven commands are instrumented with `check-no-ask` halt branches: `/z-plan` → `plan_halt` (two callsites), `/z-fix` → `fix_halt`, `/z-uplift` → `uplift_halt`, `/z-audit-plan` → `audit_halt`, `/z-audit-plan-style` → `plan_style_halt`, `/z-review-all` → `review_halt` (+ `.review_state.json` resume), `/z-execute` → `task_halt` + `implement_end` (second review failure only).

**Read-only utility commands:** `/z-personas` inspects the persona registry and current role bindings (subcommands: list, roles, validate, read, where); never writes. `/z-context-budget` analyzes context utilization from z-harness telemetry via `scripts/context-budget.py` and surfaces actionable savings recommendations. `/z-evaluate` analyzes a completed session archive via `scripts/evaluate-session.py` for patterns worth preserving as memories or skills; surfaces candidates with a `/z-suggest-memory` recommendation. `/z-debt` scans for `z:` debt markers and renders a grouped ledger to stdout; no LLM analysis, no subagent dispatch; `--save` writes to `Z-DEBT.md`. `/z-setup` is the configuration cockpit: inspect resolved state (default), run guided wizard (`wizard [--scope <name>]`), or apply a posture preset (`apply --posture <name>`); delegates to `scripts/setup.py`. `/z-verify` is an interactive understanding command that reconstructs what a codebase feature actually does, cross-references against what was intended, and converges on a verified model; delegates to `skills/z-verify/SKILL.md`.

- Overnight pipeline — `/z-overnight` is a meta-orchestrator that chains any valid sub-command sequence unattended via `Z_HARNESS_NO_ASK=halt`. It relies on `check-no-ask` instrumentation in sub-commands to halt cleanly at interactive gates; unregistered callsites block the chain.

- check-no-ask / halt-branch network — The seven instrumented commands (`z-plan`, `z-fix`, `z-uplift`, `z-audit-plan`, `z-audit-plan-style`, `z-review-all`, `z-execute`) each expose named halt events that `/z-overnight` detects via `scripts/run-status.sh classify`. `/z-review-all` additionally writes a partial `.review_state.json` on halt so re-invocation can resume at Phase 3.7.

## Command catalogue

### Pre-planning

- **`/z-grill <topic>`** — Depth-first requirements interview. One question at a time with a recommended answer; self-serves codebase questions via Explore (Haiku). Terminates adaptively; standing stop offer. Stages draft to `<plans-base>/.grill-pending.md`; finalizes to `$Z_HARNESS_PLAN_DIR/<slug>/GRILL.md`. GRILL.md is automatically detected as a precontext artifact by `/z-plan` and `/z-brainstorm`. Cost target: low.
- **`/z-sharpen [raw idea]`** — Conversational bounded idea-sharpener. Probes, reframes, and converges a vague idea into a crisp buildable problem statement. Bounded — stops once the idea is buildable; never exhaustively interrogates every dimension (that is `/z-grill`'s job). Writes `GRILL.md` as precontext. Auto-invoked as `/z-brainstorm` Phase 0 when the topic is vague. Cost target: low.

### Reporting completed work

- **`/z-report <target> [summary|standard|deep] [--profile=<profile>]`** — Communicates completed work and evidence as one profile-aware narrative: internal status, technical handoff, external/shareable update, backtest writeup, or deep internal audit. Use it for feature writeups, backtests, and professional handoffs; use `/z-explain` or `/z-learn` only when the reader needs code-level study after the report.

### Understanding code

- **`/z-explain <target> [lens]`** / **`/z-explain --repo orientation [--surface=auto|off|force]`** — One-shot structured explanation at a chosen depth lens: orientation, walkthrough, deep, or audit-brief. Repo orientation uses bounded surface mapping but still returns exactly one answer at one lens; `--surface=off` preserves the current grounding path. Every code claim cites `file:line`. Recommends `/z-learn` when the topic warrants interactive exploration; route feature writeups/backtests/handoffs to `/z-report`. Cost target: low.
- **`/z-learn <target>`** — Interactive tutor for progressive disclosure over code/system understanding. Same four lenses; one teaching chunk per turn with a standing navigation menu. Resumable via `<plans-base>/.learn-pending.md`; optional `LEARN.md` on finalize. Ingests prior `/z-explain` context. It does not produce completed-work reports; use `/z-report` for that. Cost target: low–medium.
- **`/z-verify [--slug <slug> | --path <file-or-dir> | --concept <name>]`** — Interactive understanding. Reconstructs what a codebase feature actually does, cross-references against what was intended, and converges on a verified model. Delegates to `skills/z-verify/SKILL.md`.

### Ideation and research

- **`/z-brainstorm <topic>`** — Cheap parallel idea generation with a conversational discussion/selection tail. Phase 0: (a) sharpen-vs-skip gate — if topic is vague, auto-invokes `/z-sharpen` inline; (b) NL count parse — extracts desired ideator count N (default 3); (c) scope probe (LIGHT/MEDIUM/HEAVY) with single-file fast-path; (d) wide×HEAVY suppression. Phase 2a draws 3 distinct `ideator` personas when `brainstorm.personas` ON. **Wide mode (N > 3):** conversational cost gate (no popup); phased overflow waves; `ideator-clusterer` (Haiku) collapses N framings → K distinct directions. Phase 3: ranked prose briefing — ends the turn; orchestrator MUST wait for the user's reply (never auto-decides). Phase 4 LIGHT/MEDIUM: conversational discussion loop; `synthesized` is the default expected outcome for discussion-born hybrids. Phase 4 HEAVY: ranked-pair (chunk × framing) prose briefing + end-turn. Produces `BRAINSTORM.md`. Cost target: ≤200K tokens.
- **`/z-map <question>`** — Terrain mapping via parallel Explores + cross-LLM critique. No recommendations — terrain only. Produces `MAP.md`. Cost target: ≤2M tokens.

## Edge cases / gotchas

- `/z-audit-plan` is contextual-only: with no existing plan artifacts it routes to `/z-plan` rather than pretending an audit can proceed.
- `planning-router` is advisory and only used after deterministic route thresholds fail to decide; malformed or unavailable output falls back to deterministic routing or an explicit user choice.
- Artifact Scout route boundaries mirror planning route boundaries: warning-only scout output is an advisory surface only; route-capable output must write `route-decision.md`, emit `plan_route_decision`, ask the user, and stop rather than chaining into the next command.
- No-pre-gate-Agent invariant: in `/z-plan`, `/z-research`, `/z-uplift`, and `/z-plan-split`, the pre-hard-gate scout step is deterministic inventory only. The `artifact-scout` Agent and every other expensive Agent/child dispatch is forbidden until the hard cost gate has proceeded.
- Route chains prevent ping-pong. Once a chain has two entries, or a recommendation would return to the immediate prior command, the user must choose explicitly.
- `/z-execute --tasks=<path>` derives `BASE` from the tasks file directory and bypasses normal slug/tree discovery; this is how review promotion artifacts are consumed.
- Phase 9 (`z-execute`) and Phase 7 (`z-review-all`) are soft phases: all failure paths exit silently without halting the run. Phase 9 persists candidates to JSONL and emits `memory_review_complete`; there is no sequential AskUser loop in Phase 9. Phase 10 (`z-debug`) is also a soft phase but DOES have a sequential AskUser loop (capped at 3 candidates) and emits `memory_review_terminal`.
- `--from-candidate-json` on `z-suggest-memory` accepts either a file path or `-` (stdin). It is used exclusively by the automated review-agent flow; manual callers should use the interactive path instead.
- `/z-stats` Phase 4b reads `review_agent_call` events from `metrics.jsonl`; these are emitted by `/z-execute` Phase 9, `/z-review-all` Phase 7, and `/z-debug` Phase 10. If none of these phases have run yet, this section outputs nothing.
- `/z-debug` Phase 10 memory review only runs on the `status: shipped` branch; the abandoned branch emits no memory-review telemetry. Phase 10 clears `.notify-dedup-session` at the start of each fresh debug invocation.
- `/z-debug` Phase 7 fix-consult uses the fixed 5-panel when `experiment.persona_rotation=true` but does NOT draw distinct `consultant` persona prefixes for those arms — all emit `selection_source=fixed_panel`. This is by design: Phase 7 is a convergent fix-approval step.
- `/z-plan` Phases 3 and 7 draw independent sets of `consultant` personas when `personas.critique_panel` is ON. The Phase 3 draw must NOT be reused for Phase 7 — each phase uses `random-distinct-for-role consultant --count=5` independently.
- `personas.consult_eval` (advisory consult arm in `/z-audit` Phase 4a) defaults to `false` (OFF). The advisory arm's recommendation is logged under `persona_advisory_recommendation` and is NEVER merged into the neutral synthesis.
- `personas.review_eval` (advisory eval-reviewer) defaults to `true` (ON). In all cases the advisory reviewer's verdict is advisory only — it never changes pass/fail outcome and never triggers a retry or halt. The canonical implementation is the shared snippet in `skills/z-execute/SKILL.md` (`<!-- ADVISORY-EVAL-REVIEWER -->` anchor).
- `personas.implementer_retry` defaults to `"same"`. With `"same"`, the cycle-1 `persona-draw.json` anchor is reused on retry — one `persona_id` per task across all cycles. The cycle-1 anchor is NEVER overwritten on retry regardless of the knob value.
- `/z-uplift` gates on `STYLE.md` before proceeding: if absent, offers three options but does NOT auto-invoke `/z-style-init`.
- `/z-uplift` also gates on doc-staleness before proceeding; it does NOT auto-invoke `/z-maintain-docs`.
- `/z-style-init` Mode A refuses if `STYLE.md` already exists at repo root; use `--amend` or delete manually.
- Notification policy is now driven by `config.py should-notify`; do not check `Z_HARNESS_NOTIFY_LEVEL` directly in command procedures.
- The hard slug-collision check (detecting an existing PLAN.md/TASKS.md in the slug dir) always runs unconditionally in `/z-plan`, `/z-fix`, and `/z-uplift` before the resolver is consulted.
- `check-no-ask` is fail-closed for overnight: it handles the `Z_HARNESS_ASK_ALL=1` + `Z_HARNESS_NO_ASK=halt` conflict as exit code 5 (hard config-conflict error, not a silent skip).
- `/z-overnight` sets `Z_HARNESS_NO_ASK=halt` ONLY immediately around each Skill call; the parent orchestrator's own `AskUserQuestion` prompts run with `NO_ASK` unset.
- `/z-overnight` v1 known limit: only 12 AskUserQuestion callsites participate in halt-from-ask; unregistered callsites block the chain. Run `scripts/lint-askuser.sh --strict` to audit before launching.
- `/z-attend` Invariant 1 (fail-safe): a gate with no explicit category resolves to `ask`, NEVER `mechanical_proceed`. Mis-surfacing requires an explicit wrong tag, not an omission. `/z-attend` Invariant 2: gate policy lives in `z-attend.md`; sequencing and state mechanics live in `chain-runner.sh` — never hardcode the step list in `z-attend.md`.
- `/z-attend resume <RUN>` is a hard halt on HEAD SHA mismatch or phase/cursor disagreement in `handoff.json`. It is a WARN (not halt) on session_id unchanged or done-set/dirty drift.
- `/z-axiom-scan` never auto-approves. `/z-axiom-approve` regenerates KERNEL.md synchronously on approval — this is a synchronous write and may take a moment.
- `/z-personas` is always read-only — it never writes any file.
- `/z-context-budget` and `/z-evaluate` register/deregister in the active-plan registry in advisory-only mode. This is for visibility only; they are strictly read-only.
- `/z-debt` is read-only unless `--save` flag is explicitly passed. No LLM analysis. No auto-upgrade. No subagent dispatch.
- `/z-review-all` Phase 6.5 auto-amends ALL spec_gap findings unconditionally (blocker/major/minor); only `implementation_drift` is left as candidate fixup tasks. Phase 6.6 is skipped when both corrections and approach_concerns lists are empty.
- `/z-audit-plan` auto_split path (source==none): INTENT-mode batches ALL spec_gap into a single `/z-amend` re-freeze, not per-finding. `workflow.audit_to_amend` is SOURCE-KEYED: stored value alone does not determine behavior; resolver source is the discriminator.
- Phase 0 consumer check parses `index.view.json` as a dict (entries is an object keyed by entry-id, not a list). A list-style parse would silently report 0 running entries — the T100 fix uses `entries_obj.values()`.
- `/z-followup-confirm --via=audit` requires `--evidence=<path>`; `--via=human` is mutually exclusive with `--evidence`. Mixing the flags is a hard argument-parse error.
- `Z_HARNESS_CONSULT=off` is detected via `resolve-provider.py` returning the `none` sentinel — NOT by reading the env var directly.
- The `self-reviewer` subagent dispatched by `/z-execute` when consult=off is read-only (no Edit/Write tools). Always use `subagent_type='self-reviewer'`.
- Active-plan registry: `REG_RC == 3` means register FAILED — no record was written. If register failed, do NOT call deregister anywhere in the run.
- `/z-verify` delegates fully to `skills/z-verify/SKILL.md`; the command file itself is a one-line dispatch.
