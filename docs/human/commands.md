# Commands

> Last updated: 2026-07-11
> Covers source: skills/*/SKILL.md, agents/*.md, scripts/, z_harness_cli/, runtime/

## Overview

The `commands` concept covers the slash-command specifications that drive z-harness workflows. Command procedures live in `skills/<command>/SKILL.md`; supporting orchestration code lives in `agents/*.md`, shared `scripts/`, `z_harness_cli/`, and `runtime/`. The public prod surface is the positive manifest in `runtime.release_surface` (the canonical implementation as of the codex-prod-support/model-routing work; `z_harness_cli.release_surface` is now a thin re-export shim over it): prod packages expose only `_PROD_VISIBLE_SKILLS`/MCP tools, while source/dev checkouts additionally keep experimental research, axiom, attended, and overnight surfaces. Codex is now a core public export/release target alongside Claude and OMP (promoted from a non-core/advanced target). The prod-visible user-facing paths cover planning, debugging, fixing, implementation, review, docs maintenance, memory authoring, audits, tests, stats, skill repair, plugin updates, bulk codebase uplift, style-guide authoring, provider discovery, cross-IDE export, follow-up queue management, handoff/resume, session evaluation, context-budget analysis, code debt scanning, configuration setup, and release diagnostics.

The command surface is organized around explicit routing, durable artifacts, and a closed-loop memory layer. Commands that send notifications or apply docs call `scripts/config.py export-env` during Setup to resolve `Z_HARNESS_NOTIFY_LEVEL`, `Z_HARNESS_DOCS_ALWAYS_APPLY`, and related knobs from the layered TOML config (see `docs/human/config.md`). Notification guards are expressed as `[ "$(scripts/config.py should-notify --event <type>)" = yes ]` wrappers rather than raw env-var checks. Planning-family commands collect deterministic route signals, consult `planning-router` only when signals conflict, write `route-decision.md`, emit `plan_route_decision`, and ask the user before switching. `/z-plan` now includes an explicit Intent-vs-Full SDD mode gate before the hard cost gate; config and flags preselect the recommendation, but the gate records the actual mode choice.

**Active-plan registry lifecycle:** Run-creating commands (`/z-plan`, `/z-execute`, `/z-debug`, `/z-audit`, `/z-plan-split`) all participate in a shared active-plan registry via `scripts/active-plan-registry.py`. Each run registers itself (immediately after slug discovery and structural validation), seeds its file scope via a `scope-extractor` subagent, runs an overlap scan against concurrent sessions, sends periodic heartbeats at phase boundaries, and deregisters on completion or abort. The FINALIZE_STATUS rule governs the lifecycle: after a successful register (`REG_RC == 0`), any run-ending halt sets `FINALIZE_STATUS=aborted` and calls `deregister --status aborted` before exiting; if register failed, the command never calls deregister. Overlap is advisory by design (lockless); strict mode (`Z_HARNESS_STRICT_OVERLAP=1`) adds a single hard gate on exact path collisions. `/z-stats` Phase 1 (registry-wide header) prints the resolved base, repo-id, and active-plan count unconditionally, and also renders the human-facing table of all active plans from the registry with optional overlap detection. `/z-context-budget` registers with the registry in advisory-only mode even though it is a read-only analysis command.

**Artifact Scout preflight lifecycle:** Duplicate-work/collision scouting is split into deterministic inventory plus an optional classifier. `scripts/artifact-scout-inventory.py` writes `$BASE/archive/$RUN/artifact-scout-inventory.json` and emits `artifact_scout_inventory_complete`; the tool-less `artifact-scout` Haiku agent consumes only inline compact JSON and, when run, archives its raw response as `$BASE/archive/$RUN/artifact-scout.md`. Prod-surface direct scout hooks are `/z-plan`, `/z-plan-split`, `/z-brainstorm`, `/z-audit`, `/z-debug`, `/z-audit-plan`, and `/z-audit-plan-style`. Dev-only experimental commands may add the same scout lifecycle when those commands are present in a development install. Attended wrappers are source/dev-only and do not scout independently in prod.

Hard-gated prod-surface scout hooks (`/z-plan` and `/z-plan-split`) follow the same split even when the hard gate is later in the flow: deterministic inventory may run before the gate, but the optional `artifact-scout` Agent classifier is post-gate only. Dev-only hard-gated commands follow this invariant when present in a development install. The invariant is no pre-gate `Agent()` dispatch for scout classification or other expensive reasoning.

**Artifact Scout route boundary:** Scout output is advisory unless it explicitly returns a route recommendation whose JSON has `route_chain_effect: "write_route_decision"`. Warning-only results (`STATUS: warned`, `allowed_action: warning_only`, or `route_chain_effect: "none"`) are displayed/logged but never write `route-decision.md`, never emit `artifact_scout_route`, and never advance `route_chain`. Route-capable scout findings share the existing `route-decision.md` / `plan_route_decision` boundary: write the artifact, ask the user to switch/continue/abandon, and never auto-execute the next command.

**Generated docs boundary:** LLM concept JSON (`docs/llm/INDEX.json` and `docs/llm/*.json`) is generated/maintained material. Keep concept docs fresh through `/z-maintain-docs` and `doc-updater`; do not perform ad hoc index surgery outside that maintenance path.

`/z-resume` is the command-family boundary for work-thread recovery: use it when the user asks "what was I doing?", "where did this plan/run/worktree end up?", or "how do I continue safely?" It can recover fuzzy topics, exact slugs/runs, branch/worktree anchors, and cross-repo evidence; it stops on ambiguity and treats memories/follow-ups as side evidence only.

`missing` is a source-health fact, not a negative duplicate-work proof: the classifier must not treat a missing archive/registry/worktree source as evidence that no matching artifact or peer exists.

**Follow-up sink and Phase 0 consumer check:** `/z-review-all` Phase 3.7.5 routes non-halting review findings into the project follow-up sink via `scripts/sink-add.sh` and `scripts/parse-followups-block.py`. `/z-execute` and `/z-review-all` all run a Phase 0 concurrent follow-up consumer check before any task dispatch. The check reads `z-harness/followups/index.view.json`, counts entries with `status == "running"` using a dict-safe parse (`entries` is a dict keyed by entry-id, not a list), and halts with `implement_halted_followup_running` (implement commands) or `review_halted_followup_running` (review command) if any are running. The six `/z-followup-*` commands form the consumer interface for the follow-up sink. All six carry a nest guard that blocks invocation from within a running follow-up entry's recommended command (`Z_HARNESS_FOLLOWUP_CALLER_DEPTH >= 1`).

**Scope probe (v1a) and brainstorm conversational tail:** `/z-audit` and `/z-brainstorm` run a Haiku `scope-probe` subagent as Phase 0 to classify the topic as LIGHT / MEDIUM / HEAVY. Both commands additionally have a Phase 0 fast-path: when the target is a single file path, Phase 0 is skipped and the target is auto-classified as LIGHT (emitting `scope_probe_skipped_fast_path`). `/z-brainstorm` Phase 0 first runs the shared `z-sharpen` reusable inline component when `GRILL.md` is absent (the `/z-sharpen` wrapper is not invoked), then parses the desired ideator count N from topic text (default 3; emits `count_parsed`). When N > 3 (wide mode), a conversational cost gate ends the turn before overflow ideators dispatch. Phase 3 writes `BRAINSTORM.md`, presents a ranked briefing, and hard-stops for the user's reply.

**Amendment-brief overhaul in audit/review:** `/z-review-all` Phase 6.5 unconditionally auto-amends every `amendment_proposal` (spec_gap class) via `/z-amend` (blocker/major/minor all auto-amend; implementation_drift stays as candidate fixup tasks) — Phase 6.5's step 3 excludes any finding that touches a `[x]` completed task, so `/z-amend`'s own Phase 4 gate always finds an empty Touched-but-completed-tasks list and auto-proceeds; there is no `--skip-user-gate` flag. Phase 6.6 renders a unified amendment brief via `scripts/amendment-brief.py` (corrections = Phase 6.5 spec_gaps, approach_concerns = premise_failure escalations); writes `amendment-brief.md` to archive; skipped when both lists are empty. `/z-audit-plan` Phase 5 default (source==none) is `auto_split`: in INTENT-mode, all spec_gap findings batch into ONE `/z-amend` call (single contract re-freeze); legacy-mode is per-finding; premise_failure rendered via `amendment-brief.py` as conversational prose. `force_ask` fires only when `amend-gate-decision.py` returns `force_ask` (explicit config/memory ask/prefill preference). `workflow.audit_to_amend` is SOURCE-KEYED: stored value alone does not determine behavior; resolver source is the discriminator.

**Development-only attended chain (`/z-attend`):** Present only in source/dev checkouts. It is physically excluded from prod tarballs/MCP tools by `runtime.release_surface`, along with `/z-overnight`; do not present either command as available from an installed prod package.

**Development-only axiom lifecycle commands:** The five `z-axiom-*` skills remain source/dev surfaces. `/z-axiom-scan` mines candidate axioms from interaction history via the `axiom-extractor` agent; `--historical` triggers a full `metrics.jsonl` scan; it proposes only, never auto-approves. `/z-axiom-list` renders a filtered read-only table from the store. `/z-axiom-approve` shows the candidate, evidence, and falsifiability state; requires explicit user confirmation before approving; triggers synchronous KERNEL.md regeneration on approval. `/z-axiom-reject` tombstones a candidate or approved axiom. `/z-axiom-edit` edits a field and re-validates the graph + regenerates the kernel for approved records. These commands and their axiom docs/schema/scripts are excluded from prod release artifacts.

**Resolver hooks and elevation proposer:** Several commands integrate `scripts/config.py resolve-question <question_id>` to consult stored preferences before presenting `AskUserQuestion` gates. The resolver returns `{result: skip|prefill|ask, default, source}` and the command branches accordingly. After major user-gate decisions, `/z-audit-plan` (Phase 9), `/z-audit-plan-style` (Phase 9), and `/z-amend` (Phase 9) run an Elevation Proposer via `scripts/propose-prefs.py --check <cmd>`. Six commands are instrumented with `check-no-ask` halt branches: `/z-plan` → `plan_halt` (two callsites), `/z-fix` → `fix_halt`, `/z-audit-plan` → `audit_halt`, `/z-audit-plan-style` → `plan_style_halt`, `/z-review-all` → `review_halt` (+ `.review_state.json` resume), `/z-execute` → `task_halt` + `implement_end` (second review failure only).

**Read-only utility commands:** `/z-context-budget` analyzes context utilization from z-harness telemetry via `scripts/context-budget.py` and surfaces actionable savings recommendations. `/z-debt` scans for `z:` debt markers and renders a grouped ledger to stdout; no LLM analysis, no subagent dispatch; `--save` writes to `Z-DEBT.md`. `/z-setup` is the configuration cockpit: inspect resolved state (default), run guided wizard (`wizard [--scope <name>]`), or apply a posture preset (`apply --posture <name>`); delegates to `scripts/setup.py`.

## Prod-visible command catalogue

The catalogue below is manifest-aligned with `runtime.release_surface` (re-exported for compatibility as `z_harness_cli.release_surface`) for prod packages and prod MCP tool registration. Commands physically excluded from prod (`/z-attend`, `/z-explore`, `/z-overnight`, `/z-research`, and `z-axiom-*`) are listed separately under "Development-only / prod-excluded commands" and must not be advertised as installed prod commands.

### Pre-planning

- **`/z-grill <topic>`** — Depth-first requirements interview. One question at a time with a recommended answer; self-serves codebase questions via Explore (Haiku). Terminates adaptively; standing stop offer. Stages draft to `<plans-base>/.grill-pending.md`; finalizes to `$Z_HARNESS_PLAN_DIR/<slug>/GRILL.md`. GRILL.md is automatically detected as a precontext artifact by `/z-plan` and `/z-brainstorm`. Cost target: low.
- **`/z-sharpen [raw idea]`** — Reusable bounded idea-sharpener plus slash-command wrapper. The shared component probes, reframes, and converges a vague idea into `proceed`, `sharpen_more`, or `route_to_brainstorm` with `GRILL.md` content when ready. The wrapper writes `GRILL.md` as precontext and recommends the next command without invoking it. Cost target: low.

### Reporting completed work

- **`/z-report <target> [summary|standard|deep] [--profile=<profile>]`** — Communicates completed work and evidence as one profile-aware narrative: internal status, technical handoff, external/shareable update, backtest writeup, or deep internal audit. Use it for feature writeups, backtests, and professional handoffs; use `/z-explain` or `/z-learn` only when the reader needs code-level study after the report.
- **`/z-resume [topic|current|latest|--slug <slug>|--run <run-id>|--branch <name>|--worktree <path>] [--json|--noninteractive] [--report ...]`** — Recovers what work thread you were on and how to continue safely. Use it for fuzzy prior-work topics, exact run/slug selection, branch/worktree recovery, cross-repo source citations, and ambiguity-aware reorientation. It is read-only; memories and follow-ups are side evidence only; `--report` delegates to `/z-report` only after target selection.

### Understanding code / Terrain

- **`/z-explain <target> [lens]`** / **`/z-explain --repo orientation [--surface=auto|off|force]`** — One-shot structured explanation at a chosen depth lens: orientation, walkthrough, deep, or audit-brief. Repo orientation uses bounded surface mapping but still returns exactly one answer at one lens; `--surface=off` preserves the current grounding path. Every code claim cites `file:line`. Recommends `/z-learn` when the topic warrants interactive exploration; routes work-thread continuation/reorientation to `/z-resume`; routes feature writeups/backtests/handoffs to `/z-report`. Source/dev checkouts additionally have `/z-explore` for depth-scaled terrain discovery; prod packages do not expose it. Cost target: low.
- **`/z-learn <target>`** — Interactive tutor for progressive disclosure over code/system understanding. Same four lenses; one teaching chunk per turn with a standing navigation menu. Resumable via `<plans-base>/.learn-pending.md`; optional `LEARN.md` on finalize. Ingests prior `/z-explain` context. It does not produce completed-work reports or recover plan/run/worktree state; use `/z-report` for reporting and `/z-resume` for work-thread continuation/reorientation. Cost target: low–medium.

### Ideation and research

- **`/z-brainstorm <topic>`** — Cheap parallel idea generation with a conversational discussion/selection tail. Phase 0: (a) when `GRILL.md` is absent, run the shared `z-sharpen` component inline, not the `/z-sharpen` wrapper; component recommendations are advisory and never auto-dispatch `/z-plan`; (b) NL count parse extracts desired ideator count N (default 3); (c) scope probe (LIGHT/MEDIUM/HEAVY) with single-file fast-path; (d) wide×HEAVY suppression. Phase 2a always dispatches 3 fixed-vendor ideators (Claude/Codex/Gemini) in parallel — vendor diversity, not persona rotation. **Wide mode (N > 3):** conversational cost gate (no popup); phased overflow waves; `ideator-clusterer` (Haiku) collapses N framings → K distinct directions. Phase 3: ranked prose briefing — ends the turn; orchestrator MUST wait for the user's reply (never auto-decides). Phase 4 LIGHT/MEDIUM: conversational discussion loop; synthesized choices are written only after confirmation.
- **Source/dev-only note:** `/z-research` is not a prod-visible command. It remains an expensive research meta-orchestrator in development installs only.

### Planning

- **`/z-plan <task>`** — Conversational intent compiler: sharpen always first; ask whether to run optional `/z-brainstorm`; consume selected framing if present; draft `INTENT.md` from sharpened problem + framing + targeted grounding; iterate 1–2 times with the user; run LLM concern/decision flags and ask whether to fold in `/z-audit-plan`; then a single unified prose plan-brief gate (approve / reject-shortcuts / amend / grill the draft / route back / stop) replaces the old per-decision popup sequence; on approval, generate `TASKS.md`, an initial append-only `work-graph.json` known-work DAG, task-to-intent mapping, workstreams/execution strategy, `HANDOFF.md`, and watcher-readable checkpoint metadata for `/z-execute`. `--full` keeps the legacy detailed SDD path (`SPEC.md` + `PLAN.md` + `TASKS.md`).
- **`/z-plan-split <topic>`** — Pre-emptive scope splitter for sprawling topics. Proposes 2-6 narrow clusters; reconciles overlaps into `SHARED-CONCERNS.md` + `MANIFEST.md`. Active-plan registry lifecycle. Supports Hermes multi-session fanout: ensures `workstreams.json` exists and emits a fanout payload consumed via MCP `so_start_fanout` to start one grouped child session per ready workstream.
- **`/z-test`** — Semantic test-case planner. Reads SPEC/PLAN/TASKS, drafts non-trivial tests, cross-consults, writes `TESTS.md`.

### Implementation

On second review failure: `check-no-ask` gate for `workflow.implement_all_proceed`. Implementer model resolved via native model routing. When `Z_HARNESS_CONSULT=off`, `self-reviewer` subagent replaces external codex-reviewer. ## Edge cases / gotchas

- `/z-audit-plan` is contextual-only: with no existing plan artifacts it routes to `/z-plan` rather than pretending an audit can proceed.
- `planning-router` is advisory and only used after deterministic route thresholds fail to decide; malformed or unavailable output falls back to deterministic routing or an explicit user choice.
- Artifact Scout route boundaries mirror planning route boundaries: warning-only scout output is an advisory surface only; route-capable output must write `route-decision.md`, emit `plan_route_decision`, ask the user, and stop rather than chaining into the next command.
- No-pre-gate-Agent invariant: in prod-visible `/z-plan` and `/z-plan-split`, and in source/dev-only `/z-research`, the pre-hard-gate scout step is deterministic inventory only. The `artifact-scout` Agent and every other expensive Agent/child dispatch is forbidden until the hard cost gate has proceeded.
- Route chains prevent ping-pong. Once a chain has two entries, or a recommendation would return to the immediate prior command, the user must choose explicitly.
- `/z-plan` post-artifact route checks and final handoff gate are non-auto-dispatch boundaries: they can recommend `/z-sharpen`, `/z-brainstorm`, `/z-audit-plan`, `/z-execute`, or `/z-amend`, but the user must choose and run the next command.
- Quick planning guidance is `/z-plan --quick`. Deprecated `/z-light-plan`, `/z-plan-light`, and `light-plan` wording are historical compatibility references only, not active command guidance.
- `/z-brainstorm` uses the shared z-sharpen component, not the `/z-sharpen` command wrapper. A component recommendation is guidance inside the caller's lifecycle, not permission to launch another command.
- `/z-execute --tasks=<path>` derives `BASE` from the tasks file directory and bypasses normal slug/tree discovery; this is how review promotion artifacts are consumed.
- Phase 9 (`z-execute`) and Phase 7 (`z-review-all`) are soft phases: all failure paths exit silently without halting the run. Phase 9 persists candidates to JSONL and emits `memory_review_complete`; there is no sequential AskUser loop in Phase 9. Phase 10 (`z-debug`) is also a soft phase but DOES have a sequential AskUser loop (capped at 3 candidates) and emits `memory_review_terminal`.
- `--from-candidate-json` on `z-suggest-memory` accepts either a file path or `-` (stdin). It is used exclusively by the automated review-agent flow; manual callers should use the interactive path instead.
- `/z-stats` no longer surfaces memory-review activity as of the skill-overhaul-phase1 rewrite (the former Phase 4b `review_agent_call` tally was dropped, not renumbered — `scripts/stats.py` has no memory-review subcommand). `/z-execute` Phase 9, `/z-review-all` Phase 7, and `/z-debug` Phase 10 still emit `review_agent_call` events to `metrics.jsonl`; inspect that file directly for history.
- `/z-debug` Phase 10 memory review only runs on the `status: shipped` branch; the abandoned branch emits no memory-review telemetry. Phase 10 clears `.notify-dedup-session` at the start of each fresh debug invocation.
- `/z-style-init` Mode A refuses if `STYLE.md` already exists at repo root; use `--amend` or delete manually.
- Notification policy is now driven by `config.py should-notify`; do not check `Z_HARNESS_NOTIFY_LEVEL` directly in command procedures.
- The hard slug-collision check (detecting an existing PLAN.md/TASKS.md in the slug dir) always runs unconditionally in `/z-plan` and `/z-fix` before the resolver is consulted.
- Source/dev-only `check-no-ask` overnight behavior is fail-closed: it handles the `Z_HARNESS_ASK_ALL=1` + `Z_HARNESS_NO_ASK=halt` conflict as exit code 5 (hard config-conflict error, not a silent skip).
- Source/dev-only `/z-overnight` sets `Z_HARNESS_NO_ASK=halt` ONLY immediately around each Skill call; the parent orchestrator's own `AskUserQuestion` prompts run with `NO_ASK` unset.
- Source/dev-only `/z-overnight` v1 known limit: only 12 AskUserQuestion callsites participate in halt-from-ask; unregistered callsites block the chain. Run `scripts/lint-askuser.sh --strict` to audit before launching.
- Source/dev-only `/z-attend` Invariant 1 (fail-safe): a gate with no explicit category resolves to `ask`, NEVER `mechanical_proceed`. Mis-surfacing requires an explicit wrong tag, not an omission. `/z-attend` Invariant 2: gate policy lives in `z-attend.md`; sequencing and state mechanics live in `chain-runner.sh` — never hardcode the step list in `z-attend.md`.
- Source/dev-only `/z-attend resume <RUN>` is a hard halt on HEAD SHA mismatch or phase/cursor disagreement in `handoff.json`. It is a WARN (not halt) on session_id unchanged or done-set/dirty drift.
- Source/dev-only `/z-axiom-scan` never auto-approves. `/z-axiom-approve` regenerates KERNEL.md synchronously on approval — this is a synchronous write and may take a moment.
- `/z-context-budget` registers/deregisters in the active-plan registry in advisory-only mode. This is for visibility only; it is strictly read-only.
- The personas subsystem (`personas/` directory, `resolve-persona.py`/`.sh`, and per-command persona-rotation config keys like `personas.audit`/`personas.consult_eval`/`personas.review_eval`/`brainstorm.personas`) was fully excised in skill-overhaul-phase1: `/z-audit`'s dimension auditors, `/z-brainstorm`'s 3 fixed-vendor ideators, `/z-execute` (no more Step 5.0 persona-rotation block), and `/z-fix`'s Codex safety-gate review no longer have a persona-selection step. `skills/z-export/SKILL.md` was NOT part of this rewrite and still describes exporting `personas/` content — but the `personas/` source directory itself has been deleted; this is a real, pre-existing inconsistency left for a follow-up doc-updater pass, not something this refresh corrected.
- `/z-amend`'s `--skip-user-gate` flag no longer exists (neither does `/z-review-all`'s or `/z-audit-plan`'s use of it); the Phase 4 user gate is now purely data-driven off the Touched-but-completed-tasks list computed in Phase 3 — any `[x]`-task-touching amendment always forces the conversational gate, and callers cannot bypass it with a flag.
- `/z-stats` was rewritten to 156 lines with entirely renumbered phases (Phase 1 = registry-wide header, was Phase 0b) and now delegates everything to `scripts/stats.py` / `scripts/estimate-tokens.py`; the former Phase 4b memory-review-activity section was dropped, not renumbered — do not describe `/z-stats` as surfacing memory-review history.
- `/z-debt` is read-only unless `--save` flag is explicitly passed. No LLM analysis. No auto-upgrade. No subagent dispatch.
- `/z-review-all` Phase 6.5 auto-amends ALL spec_gap findings unconditionally (blocker/major/minor); only `implementation_drift` is left as candidate fixup tasks. Phase 6.6 is skipped when both corrections and approach_concerns lists are empty.
- `/z-audit-plan` auto_split path (source==none): INTENT-mode batches ALL spec_gap into a single `/z-amend` re-freeze, not per-finding. `workflow.audit_to_amend` is SOURCE-KEYED: stored value alone does not determine behavior; resolver source is the discriminator.
- Phase 0 consumer check parses `index.view.json` as a dict (entries is an object keyed by entry-id, not a list). A list-style parse would silently report 0 running entries — the T100 fix uses `entries_obj.values()`.
- `/z-followup-confirm --via=audit` requires `--evidence=<path>`; `--via=human` is mutually exclusive with `--evidence`. Mixing the flags is a hard argument-parse error.
- `Z_HARNESS_CONSULT=off` is detected via `resolve-provider.py` returning the `none` sentinel — NOT by reading the env var directly.
- The `self-reviewer` subagent dispatched by `/z-execute` when consult=off is read-only (no Edit/Write tools). Always use `subagent_type='self-reviewer'`.
- Active-plan registry: `REG_RC == 3` means register FAILED — no record was written. If register failed, do NOT call deregister anywhere in the run.
- `/z-suggest-memory`'s general/interactive memory-authoring procedure body is a known-broken self-referential stub (line ~60 of `skills/z-suggest-memory/SKILL.md` says to read-and-execute its own file). Only the `--kind routing-preference` structured-write mode and the `--source`-prefix conventions table are intact and safe to describe as working.
- `/z-execute` N=2 cross-cluster parallel dispatch requires `workflow.hermes_enabled=true` in addition to `overlap_count==0` (default `hermes_enabled=false` → always serial). Do not describe `overlap_count==0` alone as sufficient to trigger cross-cluster parallelism.
- `/z-execute` implementer model selection now runs through native `[model_routing.implementer]`/`[model_classes]` config resolution (`runtime.dispatch.dispatcher.resolve_implementer_model`) rather than a hardcoded tier→model map; the resolved route is applied only when the host confirms per-call model override support, otherwise it is advisory telemetry only (`subagent_model_override_applied`/`override_support`).
- `/z-execute` INTENT-mode `divergence_signal` halts are a distinct failure path from ordinary acceptance-evaluator `VERDICT: continue` — they mean the frozen INTENT itself has been invalidated (not just incomplete), and the recommended recovery is `/z-amend --reopen-intent <slug>`, not simply re-running `/z-execute`.
- The canonical location of the prod-visibility manifest moved from `z_harness_cli.release_surface` to `runtime.release_surface`; `z_harness_cli.release_surface` still exists but is now only a re-export shim. New references should cite `runtime.release_surface`.
- Percentage-based adaptive context compaction (`scripts/check-compaction.sh` / `scripts/write-clear-checkpoint.sh` at threshold-evaluated seams, not fixed points) is now wired through `/z-plan`, `/z-execute`, `/z-audit`, `/z-debug`, `/z-review-all`, `/z-test`, `/z-research`, `/z-explore`, and `/z-handoff` — treat this as a shared cross-command mechanism, not a per-command bespoke checkpoint.
