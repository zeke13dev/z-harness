## Overview

The `commands` concept covers the slash-command specifications that drive z-harness workflows. Each command lives as a Markdown procedure under `commands/` and defines a user-facing orchestration path: planning, research, debugging, fixing, implementation, review, docs maintenance, memory authoring, audits, tests, stats, skill repair, plugin updates, bulk codebase uplift, style-guide authoring, provider discovery, cross-IDE export, unattended overnight pipeline execution, follow-up queue management, and diagnostics.

The command surface is organized around explicit routing, durable artifacts, and a closed-loop memory layer. Commands that send notifications or apply docs call `scripts/config.py export-env` during Setup to resolve `Z_HARNESS_NOTIFY_LEVEL`, `Z_HARNESS_DOCS_ALWAYS_APPLY`, and related knobs from the layered TOML config (see `docs/human/config.md`); `/z-do` and `/z-plan` are the canonical adopters. Notification guards are expressed as `[ "$(scripts/config.py should-notify --event <type>)" = yes ]` wrappers rather than raw env-var checks. Planning-family commands collect deterministic route signals, consult `planning-router` only when signals conflict, write `route-decision.md`, emit `plan_route_decision`, and ask the user before switching. `/z-plan` step 9c runs a consolidated freshness gate that covers docs-staleness, RESEARCH.md/MAP.md citation freshness in a single `AskUserQuestion`; a Proceed-with-all-stale choice emits `precontext_freshness_acknowledged` and sets `to_command: null` in `plan_route_decision` (so `/z-stats` can distinguish it from a real remedy route). Review-family commands preserve evidence separately from promotion artifacts and route actionable findings through `/z-implement-all --tasks`. Both `/z-implement-all` (Phase 9) and `/z-review-all` (Phase 7) close the loop by running `run-memory-review.sh` after each plan completes, dispatching a `review-agent` to surface memory candidates, persisting them as JSONL, and notifying the user to review with `/z-suggest-memory --from-candidate-json`; accepted candidates are ingested by that command. `/z-implement-all` Phase 9 emits `memory_review_complete` when candidates are written; it does NOT present an in-phase AskUserQuestion loop. `/z-debug` (Phase 10) also runs `run-memory-review.sh` after a shipped fix and uses a 5-line stdout contract (line 5 = DEBUG.md path); Phase 10 does have a sequential AskUser loop capped at 3 candidates and its terminal event is `memory_review_terminal`. The abandoned branch skips memory review entirely. `/z-audit-plan-style` audits plan artifacts (SPEC.md, PLAN.md, TASKS.md) for code-quality issues before any code is written — it requires STYLE.md (hard gate), dispatches a `plan-style-reviewer` agent internally, and emits `PLAN_STYLE_AUDIT.md` with BLOCKER/MAJOR/MINOR findings shaped for `/z-amend`. `/z-uplift` adds a tiered bulk-uplift path: it decomposes the repo into components, runs a cross-cutting pass, dispatches per-component audits, produces per-component TASKS.md files, and drives sequential implementation via `/z-implement-all`. `/z-style-init` authors a STYLE.md grounded in the repo's most idiomatic files and a cross-LLM critique; its `--amend` mode mines repeated dismissals from past MR-REVIEW runs to propose new rules. `/z-providers-discover` probes PATH for known LLM CLIs and writes a `providers.json` with interactively-confirmed role bindings. `/z-export` runs per-target adapter scripts to translate z-harness sources into IDE-specific formats under `exports/`.

**Active-plan registry lifecycle:** Run-creating commands (`/z-plan`, `/z-implement-all`, `/z-implement-next`, `/z-do`, `/z-debug`, `/z-audit`, `/z-plan-split`) all participate in a shared active-plan registry via `scripts/active-plan-registry.py`. Each run registers itself (immediately after slug discovery and structural validation), seeds its file scope via a `scope-extractor` subagent, runs an overlap scan against concurrent sessions, sends periodic heartbeats at phase boundaries, and deregisters on completion or abort. The FINALIZE_STATUS rule governs the lifecycle: after a successful register (`REG_RC == 0`), any run-ending halt sets `FINALIZE_STATUS=aborted` and calls `deregister --status aborted` before exiting; normal completion deregisters with `complete`; if register failed (no record written), the command never calls deregister. Overlap is advisory by design (lockless, safe only because advisory); strict mode (`Z_HARNESS_STRICT_OVERLAP=1`) adds a single hard gate on exact path collisions. `/z-stats` Phase 0b now prints the resolved base, repo-id, and active-plan count as a header (unconditionally, reading the registry). `/z-where` is a new read-only diagnostic command (no LLM calls, no subagent dispatch) that prints the resolved base + repo-id and a table of all active plans from the registry, with optional overlap detection against a specific run-id.

**Persona rotation and personas-everywhere (experiment, on by default):** When `experiment.persona_rotation=true`, `/z-implement-all` and `/z-implement-next` call `resolve-persona.py random-for-role implementer` before each task attempt; every `experiment.control_every_n`-th attempt uses `forced-control` (boring-anchor) instead. The draw result is persisted to `$BASE/archive/tasks/<task-id>/persona-draw.json`; resumes reuse the same draw, retries respect the `personas.implementer_retry` knob (`"same"` default: same persona across all cycles of a task; `"new"`: fresh draw excluding prior persona, written to per-cycle sidecar `persona-draw-v<CYCLE>.json`). Both commands dispatch a dual reviewer (base codex + one advisory random-arm) instead of just the base reviewer when `personas.review_eval` is also on (default ON); the random-arm verdict never changes halt/retry behavior. Outcome is logged as `persona_attempt_outcome` at attempt close. `/z-plan` (Phases 3 and 7) and `/z-debug` (Phases 3a, 3b) use a fixed 5-panel consult (agy, cursor@claude-4.6-sonnet, cursor@grok-4.3, cursor@composer-2.5, codex-cli) when `experiment.persona_rotation=true`; the `personas.critique_panel` sub-knob (default ON) governs whether each 5-panel arm additionally draws a distinct `consultant` persona prefix — Phases 3 and 7 draw independently; Phases 3a and 3b in `/z-debug` share the same draw. Phase 7 (fix-consult) in `/z-debug` uses the fixed 5-panel for selection but emits `selection_source=fixed_panel` for all arms (no persona prefix draw for fix-consult). `/z-brainstorm` Phase 2a draws 3 distinct `ideator` personas when `brainstorm.personas` is ON (default ON) — persona diversity layered on top of vendor diversity; the knob OFF is a true no-op leaving dispatch byte-identical to pre-feature behavior. `/z-audit` Phase 2a draws up to 4 distinct `audit_persona` personas (one per dimension auditor) when `personas.audit` is ON (default ON); both `/z-audit` Phase 4a and `/z-plan-light` Phase 3 support a measured advisory consult arm (`personas.consult_eval`, default OFF) that runs in parallel with the two neutral consultants but is advisory only — its recommendation is logged under `persona_advisory_recommendation` and never folded into the neutral synthesis. `/z-fix`, `/z-do`, `/z-plan-light`, `/z-implement-all`, and `/z-implement-next` all gate an advisory eval-reviewer at their Codex review gates via `personas.review_eval` (default ON); the canonical "Advisory eval-reviewer (shared snippet)" lives in `commands/z-implement-all.md`. All rotation behavior is a no-op when the governing knob is off. See `docs/human/PERSONAS.md` for the full rotation protocol.

**Follow-up sink and Phase 0 consumer check:** `/z-review-all` Phase 3.7.5 routes non-halting (major/minor) review findings into the project follow-up sink via `scripts/sink-add.sh` and `scripts/parse-followups-block.py`; it emits `followups_routed_to_sink` after the batch write. `/z-implement-all`, `/z-implement-next`, and `/z-review-all` all run a **Phase 0 concurrent follow-up consumer check** before any slug discovery or task dispatch. The check reads `z-harness/followups/index.view.json` (project sink), counts entries with `status == "running"` using a dict-safe parse (T100 fix: `entries` is a dict keyed by entry-id, not a list), and halts with event `implement_halted_followup_running` (implement commands) or `review_halted_followup_running` (review command) if any are running. The six `/z-followup-*` commands form the consumer interface for the follow-up sink: list, status, next, confirm, dismiss, and refresh. All six carry a nest guard that blocks invocation from within a running follow-up entry's recommended command (`Z_HARNESS_FOLLOWUP_CALLER_DEPTH >= 1`).

**Scope probe (v1a):** `/z-audit` and `/z-brainstorm` now run a Haiku `scope-probe` subagent as Phase 0 (before Phase 1 scaffolding) to classify the topic as LIGHT / MEDIUM / HEAVY and choose the execution topology. Both commands additionally have a **Phase 0 fast-path**: when the target is a single file (short argument with no whitespace, matching a known file path), Phase 0 is skipped entirely and the target is auto-classified as LIGHT — emitting `scope_probe_skipped_fast_path` in lieu of the scope-probe Agent call. HEAVY triggers parallel sub-flow fan-out with a `scope-reconciler` agent consolidating results. `/z-audit` also accepts a `--scope-from <chunk-spec>` flag (parsed before Setup) to skip Phase 0 when already running as a HEAVY sub-flow. `/z-brainstorm` HEAVY Phase 4 presents a `(chunk × framing)` selection matrix to the user before finalizing BRAINSTORM.md.

**Resolver hooks and elevation proposer:** Several commands integrate `scripts/config.py resolve-question <question_id>` to consult stored preferences before presenting `AskUserQuestion` gates. The resolver returns `{result: skip|prefill|ask, default, source}` and the command branches accordingly: `skip` accepts the default silently and emits `askuser_skipped`; `prefill` pre-selects the default but still asks; `ask` presents the question normally (adding a conflict-resolution note when `source == "conflict"`). After major user-gate decisions, `/z-audit-plan` (Phase 9), `/z-audit-plan-style` (Phase 9), and `/z-amend` (Phase 9) run an Elevation Proposer via `scripts/propose-prefs.py --check <cmd>`. If the script detects a repeated pattern (e.g., always running z-amend after an audit), it surfaces a one-shot `AskUserQuestion` offering to persist the preference as a config entry or a `routing-preference` memory entry (via `/z-suggest-memory --kind routing-preference`). Suppression for 30 days is available via the `no` branch; the suppression state is stored in `.z-harness/.propose-suppress`. The `workflow.slug_confirm` question governs slug-name confirmation in `/z-plan`, `/z-fix`, and `/z-uplift`; the hard collision check (slug dir already contains PLAN.md/TASKS.md) runs unconditionally before the resolver is consulted — the resolver only governs the soft non-obvious-slug confirmation gate. The `workflow.audit_to_amend` question governs the post-audit action choice in `/z-audit-plan` and `/z-audit-plan-style`. `/z-suggest-memory` now accepts `--kind routing-preference` with `--question-id`, `--value`, `--strength` (weak/strong/very_strong), `--scope` (global/project), and optional `--reason`; routing-preference entries are written to `docs/llm/workflow.json` (global) or `docs/llm/workflow-<project-slug>.json` (project).

**check-no-ask + halt branches (overnight integration):** Seven commands have been retrofitted with a `check-no-ask` gate that consults `scripts/config.py check-no-ask --question-id <qid>` before each AskUserQuestion callsite that is on the overnight hot path. When `Z_HARNESS_NO_ASK=halt` is in effect (set by `/z-overnight` around each Skill call), `check-no-ask` returns `halt` instead of `proceed`, and the command emits a command-specific halt event and exits cleanly without invoking AskUserQuestion. The affected commands and their halt events are: `/z-plan` → `plan_halt` (two callsites: `workflow.slug_confirm` and `workflow.plan_decisions_approval`); `/z-fix` → `fix_halt` (`workflow.slug_confirm`); `/z-uplift` → `uplift_halt` (`workflow.slug_confirm`); `/z-audit-plan` → `audit_halt` (`workflow.audit_to_amend`); `/z-audit-plan-style` → `plan_style_halt` (`workflow.audit_to_amend`); `/z-review-all` → `review_halt` (`workflow.review_all_proceed`) with resume-from-halt support via `.review_state.json`; `/z-implement-all` → `task_halt` + `implement_end` (`workflow.implement_all_proceed`, only on second review failure). The `check-no-ask` call always precedes `resolve-question` at these callsites; a `proceed` result falls through to the normal resolver path.

**`/z-overnight` orchestrator:** Runs a comma- or arrow-separated chain of z-harness sub-commands end-to-end with no interactive gates. Accepts `<chain> [task-description]`, `preset:<name> [task-description]`, or `resume <RUN_ID>`. Built-in presets: `full-build` = `plan,test,implement-all,review-all`; `research-build` = `research,plan,test,implement-all,review-all`; `quick-build` = `plan,implement-all`. Sets `Z_HARNESS_NO_ASK=halt` only around each Skill call (Phase 3.6) and unsets it immediately after. Hard halts (slug collision, lock corruption, empty chain) are never bypassed by the overnight allowlist. Maintains `overnight-state.json` under `$BASE/archive/<RUN_ID>/` with per-step status, timing, artifact paths, and terminal event kind. Writes `MORNING_REPORT.md` via `scripts/morning-report.py` and push-notifies on completion or halt. Supports resume via `overnight-state.json` state with HEAD SHA validation. Concurrency is enforced via `$BASE/.overnight.lock` (JSON) with a `$BASE/.overnight.flock` file for atomic check-and-write; the stale threshold is `Z_HARNESS_OVERNIGHT_LOCK_STALE_S` (default 7200 seconds). The auto-decide allowlist (`AUTODECIDE_EFFECTIVE`, merged from hardcoded defaults + `Z_HARNESS_OVERNIGHT_AUTODECIDE` env override) pre-answers registered question IDs (e.g., `workflow.slug_confirm`, `workflow.audit_to_amend`). Sub-run archive identification uses directory diff (before/after snapshots, excluding `*-overnight-*` dirs). Known v1 limit: only 12 AskUserQuestion callsites participate in halt-from-ask; unregistered callsites block the chain. Run `scripts/lint-askuser.sh --strict` to audit before launching.

## How it interacts with others

- `agents` — Commands dispatch specialized subagents: implementers, reviewers, consultants, doc-updaters, doc-fetchers, auditors, cluster-planners, remote-runners, the advisory `planning-router`, the `review-agent` (memory candidate generation), the `plan-style-reviewer` (plan artifact quality review), the `bisect-isolator` (regression isolation), the `scope-probe` (Phase 0 topology classifier for /z-audit and /z-brainstorm), the `scope-reconciler-audit` / `scope-reconciler-brainstorm` (HEAVY fan-out synthesis), the `self-reviewer` (`agents/self-reviewer.md` — read-only same-model Opus self-review dispatched by `/z-implement-all` Steps 6 and 7a when `Z_HARNESS_CONSULT=off`), and the `scope-extractor` (Haiku — extracts file scope from a plan's TASKS.md for the active-plan registry). `/z-uplift` dispatches `auditor` subagents in parallel per dimension per component. `/z-style-init` dispatches Sonnet subagents for file ranking, drafting, and rule proposals.
- `scripts` — Commands rely on shared scripts for version stamping, event logging, phase timing, plan path resolution, memory flattening, remote support, `run-memory-review.sh`, `discover-providers.py`, `export-<target>.py`, `extract-dismissals.py`, `propose-prefs.py` (elevation proposer check), `run-status.sh` (sub-run classification for /z-overnight), `morning-report.py` (MORNING_REPORT.md generation for /z-overnight), `sink-add.sh` (follow-up sink writes from /z-review-all Phase 3.7.5), `parse-followups-block.py` (extract FOLLOWUPS blocks from reviewer output), `active-plan-registry.py` (register/heartbeat/overlaps/deregister for concurrent-session coordination used by all run-creating commands and queried by /z-where and /z-stats), and `resolve-persona.py` (persona draw for implementer, reviewer, consultant, audit_persona, and ideator roles — random-for-role, random-distinct-for-role, forced-control, and control-counter subcommands).
- `config` — All commands that send notifications or apply docs call `scripts/config.py export-env` during Setup to populate `Z_HARNESS_NOTIFY_LEVEL` and `Z_HARNESS_DOCS_ALWAYS_APPLY`, then guard every notification with `[ "$(config.py should-notify --event <type>)" = yes ]`. Commands that use resolver hooks call `scripts/config.py resolve-question <question_id>` before AskUserQuestion gates. Commands retrofitted with check-no-ask call `scripts/config.py check-no-ask --question-id <qid>` as a fail-closed overnight gate before each instrumented callsite; a non-zero exit (e.g. exit 5 for `Z_HARNESS_ASK_ALL=1` + `Z_HARNESS_NO_ASK=halt` conflict) causes the command to treat the result as a hard error. Persona knobs (`experiment.persona_rotation`, `personas.critique_panel`, `personas.audit`, `brainstorm.personas`, `personas.consult_eval`, `personas.review_eval`, `personas.implementer_retry`) are read via `config.py get <knob>`. The canonical reference for available knobs is `docs/human/config.md`.
- `skills` — Skills expose or wrap the command flows for different clients and are the main consumer of the command specifications. `/z-overnight` invokes sub-commands via the Skill tool.
- `followup-sink` — `/z-review-all` Phase 3.7.5 writes non-halting findings to the project sink via `scripts/sink-add.sh`; `/z-implement-all`, `/z-implement-next`, and `/z-review-all` all read `z-harness/followups/index.view.json` in Phase 0 to halt if any entry has `status=running`. The six `/z-followup-*` commands are the human-facing interface to the sink (read, status, consume, confirm, dismiss, refresh).
- `active-plan-registry` — The shared lockless registry (`scripts/active-plan-registry.py`) coordinates concurrent runs. Run-creating commands register on start and deregister on exit. `/z-where` reads it for its human-facing active-plan table. `/z-stats` Phase 0b reads the active count. Overlap is advisory; strict mode enables one hard gate.
- Review-family artifacts — `/z-audit`, `/z-review-all`, and `/z-mr-review` preserve evidence separately from promoted task artifacts; survivors are applied through `/z-implement-all --tasks <path>`.
- Planning-family route policy — `/z-plan`, `/z-plan-light`, `/z-plan-split`, `/z-map`, `/z-research`, `/z-brainstorm`, and `/z-do` share route checks that record route artifacts and never auto-execute a different command.
- Memory loop — `/z-implement-all` Phase 9 and `/z-review-all` Phase 7 both call `run-memory-review.sh`, dispatch `review-agent`, and persist candidates to JSONL; the user reviews them via `/z-suggest-memory --from-candidate-json`. Phase 9 emits `memory_review_complete` when N≥1 candidates are written (no in-phase AskUser loop). `/z-debug` Phase 10 participates in the same loop after a shipped fix (abandoned branch skips) and emits `memory_review_terminal`. `/z-stats` Phase 4b surfaces `review_agent_call` events so the user can see memory-review history.
- Plan-quality pipeline — `/z-audit-plan-style` audits plan artifacts for code-quality issues before implementation begins. It requires `STYLE.md` (hard gate, no escape), dispatches the `plan-style-reviewer` agent, uses `extract-dismissals.py` to suppress repeated past dismissals, and emits `PLAN_STYLE_AUDIT.md` shaped for direct `/z-amend` consumption.
- Uplift pipeline — `/z-uplift` is a self-contained orchestration that sits above the planning and review families: it auto-decomposes the repo, calls consultant subagents for cross-cutting analysis, delegates per-component audits to auditor subagents, and drives sequential implementation via existing `/z-implement-all` invocations. It gates on `STYLE.md` presence and doc-staleness before proceeding.
- Style pipeline — `/z-style-init` (bootstrap and amend) is a prerequisite for `/z-mr-review` style enforcement, `/z-audit-plan-style`'s hard gate, and feeds the `/z-uplift` cleanliness+design rubric. `/z-style-init --amend` consumes dismissal archives written by `/z-mr-review` runs.
- Provider configuration — `/z-providers-discover` writes `providers.json` consumed by all commands that dispatch `consultant-primary`, `consultant-secondary`, or `reviewer` subagents.
- Scope probe pipeline — `/z-audit` Phase 0 dispatches `scope-probe` (Haiku) to classify topics as LIGHT/MEDIUM/HEAVY before Phase 1, or takes the single-file fast-path emitting `scope_probe_skipped_fast_path`. HEAVY triggers N parallel `/z-audit` sub-flows via `--scope-from <abs-path>#<chunk-id>`, then dispatches `scope-reconciler-audit` to merge results; HEAVY sub-flows skip Phase 0 via `SKIP_PHASE_0=true`. `/z-brainstorm` Phase 0 uses the same `scope-probe` with axis taxonomy `[per_vendor, per_framing]` and the same single-file fast-path; HEAVY dispatches N parallel general-purpose Sonnet sub-flows and calls `scope-reconciler-brainstorm`. HEAVY Phase 4 in `/z-brainstorm` presents the `(chunk × framing)` selection matrix before finalizing BRAINSTORM.md.
- Resolver and elevation proposer pipeline — `/z-audit-plan` (Phase 9), `/z-audit-plan-style` (Phase 9), and `/z-amend` (Phase 9) all invoke `propose-prefs.py` after the finalize step. When the script identifies a repeated user pattern (e.g., always choosing amend after an audit), it surfaces a one-shot `AskUserQuestion` that routes the answer to config (via `config.py set`) or to `docs/llm/workflow.json` / `docs/llm/workflow-<project-slug>.json` (via `/z-suggest-memory --kind routing-preference`). Future resolver calls for the same `question_id` can then skip or pre-fill the gate automatically. Suppression state lives in `.z-harness/.propose-suppress` with 30-day TTL entries.
- Cross-cluster parallelism — When a tree-rooted plan's `SHARED-CONCERNS.md` reports `overlap_count: 0`, `/z-implement-all` dispatches the next two adjacent clusters in a single message (N=2 parallel), emitting a `cross_cluster_parallel` event. Plans with `overlap_count != 0` always run serially regardless of actual file-level overlap details.
- Overnight pipeline — `/z-overnight` is a meta-orchestrator that chains any valid sub-command sequence and runs it unattended via `Z_HARNESS_NO_ASK=halt`. It relies on `check-no-ask` instrumentation in sub-commands to halt cleanly at interactive gates; unregistered callsites will block the chain. Sub-run classification uses `scripts/run-status.sh`; MORNING_REPORT.md is generated by `scripts/morning-report.py`. The overnight auto-decide allowlist can be extended via `Z_HARNESS_OVERNIGHT_AUTODECIDE` env override (JSON).
- check-no-ask / halt-branch network — The seven instrumented commands (`z-plan`, `z-fix`, `z-uplift`, `z-audit-plan`, `z-audit-plan-style`, `z-review-all`, `z-implement-all`) each expose named halt events (`plan_halt`, `fix_halt`, `uplift_halt`, `audit_halt`, `plan_style_halt`, `review_halt`, `task_halt`) that `/z-overnight` detects via `scripts/run-status.sh classify`. `/z-review-all` additionally writes a partial `.review_state.json` on halt so re-invocation can resume at Phase 3.7 without re-running Phases 0–3.5.
- Personas pipeline — `scripts/resolve-persona.py` is the shared persona-draw engine. Commands call it for `random-for-role <role>`, `random-distinct-for-role <role> --count=N`, or `forced-control <role> --arm=<arm>`. Persona bodies live in persona definition files whose paths are returned via `persona_body_path`; the `runtime/dispatch/persona_prompt.py` helper strips YAML frontmatter and returns a prefixable body. The `personas.*` and `brainstorm.personas` knobs are all read via `scripts/config.py get <knob>`.

## Command catalogue (from README)

### Pre-planning

- **`/z-grill <topic>`** — Depth-first requirements interview. Asks one question at a time, states a recommended answer each time, and self-serves codebase questions via Explore (Haiku). Terminates adaptively; the user may stop early at any time. Stages draft to `<plans-base>/.grill-pending.md`; finalizes to `$Z_HARNESS_PLAN_DIR/<slug>/GRILL.md` with collision-checked slug. GRILL.md carries `status: complete` frontmatter and is automatically detected as a precontext artifact by `/z-plan` (step 9) and `/z-brainstorm` (Phase 1). Cost target: low (single conversational session).

### Understanding code

- **`/z-explain <target> [lens]`** — One-shot structured explanation at a chosen depth lens: orientation (design decisions), walkthrough (flow), deep (line-level), or audit-brief (invariants/failure modes — not a real audit). Fuzzy natural language maps to lenses. Every code claim cites `file:line`. Recommends `/z-learn` when the topic warrants interactive exploration. Cost target: low (single pass).
- **`/z-learn <target>`** — Interactive tutor for progressive disclosure. Same four lenses; one teaching chunk per turn with a standing navigation menu (deeper, next, pivot, switch lens, finalize, stop). Resumable via `<plans-base>/.learn-pending.md`; optional `LEARN.md` on finalize. Ingests prior `/z-explain` context. Cost target: low–medium (conversation-length).

Typical chain: `/z-explain src/pipeline.rs orientation` then `/z-learn src/pipeline.rs` when you want to keep going.

- **`/z-brainstorm <topic>`** — Cheap parallel idea generation across three vendor-diverse ideators. Phase 0 scope probe classifies topic as LIGHT/MEDIUM/HEAVY; single-file targets skip to LIGHT via fast-path. Phase 2a draws 3 distinct `ideator` personas when `brainstorm.personas` is ON (default ON). HEAVY fans out N parallel sub-flows per axis chunk and presents a chunk × framing matrix at Phase 4. Produces `BRAINSTORM.md`. Cost target: ≤200K tokens.
- **`/z-map <question>`** — Terrain mapping via parallel Explores + cross-LLM critique. No recommendations — terrain only. Produces `MAP.md`. Cost target: ≤2M tokens.
- **`/z-research <topic>`** — Heavy meta-orchestrator: invokes `/z-map` and/or `/z-brainstorm`, then runs an adversarial synthesis panel (3 vendor-diverse perspectives + `research-judge` Opus synthesizer) to produce `RESEARCH.md` with a 10-section schema including an approach decision matrix. Phase 1 dispatches both sub-commands in parallel when both need to run and uses event-kind fields in each sub-run's events.jsonl to distinguish their archive directories. Cost: 3–6M tokens. AskUser cost gate always runs before dispatch.

Typical chains:
- Deep research + synthesis: `/z-research → /z-plan`
- Terrain only: `/z-map → /z-brainstorm → /z-plan`
- Lighter case: `/z-brainstorm → /z-plan`
- Standard: `/z-plan` alone

- **`/z-suggest-memory`** — Author a memory entry into a concept's `docs/llm/<slug>.json`. Use `--kind routing-preference` to write a structured workflow preference entry to `docs/llm/workflow.json` (global) or `docs/llm/workflow-<project-slug>.json` (project).

### Telemetry and diagnostics

- **`/z-stats`** — Read-only progress + cost report from `metrics.jsonl` and TASKS.md. Phase 0b prints a header with resolved base, repo-id, and active-plan count (from the active-plan registry) before any slug-specific output.
- **`/z-where`** — Read-only concurrent-run diagnostic. No LLM calls, no subagent dispatch. Prints resolved base + repo-id (Phase 0), then a table of all active plans from the registry (slug, command, phase, branch, current_task, age, status) (Phase 1). Optionally shows path-overlap with a specific run via `--run-id <id>` or `Z_HARNESS_RUN_ID` (Phase 2). Robust to registry unavailability — always exits cleanly.
- Export pipeline — `/z-export` is a thin orchestration shell around `scripts/export-<target>.py` adapter scripts; it does no file I/O itself.

## Edge cases / gotchas

- `/z-audit-plan` is contextual-only: with no existing plan artifacts it routes to `/z-plan` rather than pretending an audit can proceed.
- `planning-router` is advisory and only used after deterministic route thresholds fail to decide; malformed or unavailable output falls back to deterministic routing or an explicit user choice.
- Route chains prevent ping-pong. Once a chain has two entries, or a recommendation would return to the immediate prior command, the user must choose explicitly.
- `/z-implement-all --tasks=<path>` derives `BASE` from the tasks file directory and bypasses normal slug/tree discovery; this is how review promotion artifacts are consumed.
- `z-review-all` and `z-maintain-docs --audit` have pre-consult compaction breakpoints with state files so expensive consultant phases can resume safely.
- `/z-suggest-memory` is intentionally thin: it delegates to `commands/z-suggest-memory.md`, which owns memory mutation and `MEMORIES-FLAT.md` regeneration.
- Phase 9 (`z-implement-all`) and Phase 7 (`z-review-all`) are soft phases: all failure paths (malformed agent output, skipped helper, empty candidate array) exit silently without halting the run. Phase 9 persists candidates to JSONL and emits `memory_review_complete`; there is no sequential AskUser loop in Phase 9. Phase 10 (`z-debug`) is also a soft phase but DOES have a sequential AskUser loop (capped at 3 candidates) and emits `memory_review_terminal`.
- `--from-candidate-json` on `z-suggest-memory` accepts either a file path or `-` (stdin). It is used exclusively by the automated review-agent flow; manual callers should use the interactive path instead.
- `/z-stats` Phase 4b reads `review_agent_call` events from `metrics.jsonl`; these are emitted by `/z-implement-all` Phase 9, `/z-review-all` Phase 7, and `/z-debug` Phase 10. If none of these phases have run yet, this section outputs nothing.
- `/z-debug` Phase 10 uses a 5-line stdout contract with `run-memory-review.sh`: line 1=status, line 2=cumulative_diff_path, line 3=spec_path (may be empty), line 4=tags_path, line 5=debug_md_path. Phase 10 requires `memory_review_terminal` to be emitted exactly once per invocation: the helper emits it on all skip paths; the orchestrator emits it after the user-gate loop for `ran_empty` and `needs_user` paths.
- `/z-debug` Phase 10 memory review only runs on the `status: shipped` branch; the abandoned branch emits no memory-review telemetry. The D11 push-notify policy applies to `skipped_broken_context` skip states: push-notify at most once per `(slug, skip_reason)` pair, deduplicated via `.notify-dedup-session`.
- `/z-debug` Phase 10 clears `.notify-dedup-session` at the start of each fresh debug invocation so notify dedup state from a previous session does not bleed into the current one.
- `/z-debug` Phase 2.5 (bisect fast-path) is conditional: all three gates must hold (known-good ref, reproducibility confirmed yes, scriptable repro). All non-`ok` bisect statuses fall through to Phase 3a without blocking. Bisect augments evidence and seeds Phase 3a prompts but never replaces hypothesis generation or pre-fills the winning hypothesis.
- `/z-debug` Phase 7 fix-consult uses the fixed 5-panel when `experiment.persona_rotation=true` but does NOT draw distinct `consultant` persona prefixes for those arms — all emit `selection_source=fixed_panel`. This is by design: Phase 7 is a convergent fix-approval step, not a divergent hypothesis round. Persona prefixes are only drawn for Phases 3a and 3b (the divergent rounds).
- `/z-plan` Phases 3 and 7 draw independent sets of `consultant` personas when `personas.critique_panel` is ON. The Phase 3 draw must NOT be reused for Phase 7 — each phase uses `random-distinct-for-role consultant --count=5` independently.
- `personas.consult_eval` (advisory consult arm in `/z-audit` Phase 4a and `/z-plan-light` Phase 3) defaults to `false` (OFF). The advisory arm's recommendation is logged under `persona_advisory_recommendation` and is NEVER merged into the neutral synthesis — the neutral consultants' output is the sole decision of record for both commands.
- `personas.review_eval` (advisory eval-reviewer) defaults to `true` (ON). It fires in `/z-fix`, `/z-do`, `/z-plan-light`, `/z-implement-all`, and `/z-implement-next`. In all cases the advisory reviewer's verdict is advisory only — it never changes pass/fail outcome and never triggers a retry or halt. The canonical implementation is the shared snippet in `commands/z-implement-all.md` (`<!-- ADVISORY-EVAL-REVIEWER -->` anchor); `/z-fix`, `/z-do`, and `/z-plan-light` reference it by anchor rather than copying the bash.
- `personas.implementer_retry` defaults to `"same"`. With `"same"`, the cycle-1 `persona-draw.json` anchor is reused on retry — one `persona_id` per task across all cycles. With `"new"`, a fresh draw is written to `persona-draw-v<CYCLE>.json` (per-cycle sidecar) excluding the prior persona. The cycle-1 anchor is NEVER overwritten on retry regardless of the knob value.
- `brainstorm.personas` knob OFF is a true byte-identical no-op: `*_PERSONA_PREFIX` stays empty, no draw event, no `persona_bound` emit. The ideator dispatch in `/z-brainstorm` Phase 2b is byte-identical to pre-feature behavior.
- `personas.audit` knob draws use `audit_persona` role (not `consultant`). Underflow is graceful: if the pool has fewer than 4 members, the returned array is shorter and unfilled slots run vanilla. Unfilled slots emit no `persona_bound` event.
- `/z-uplift` gates on `STYLE.md` before proceeding: if absent, it offers three options (run `/z-style-init` first, continue with degraded rubric, or abort). It does NOT auto-invoke `/z-style-init`.
- `/z-uplift` also gates on doc-staleness: if `stale_pct >= Z_HARNESS_DOC_STALENESS_THRESHOLD` (default 20%), it presents an `AskUserQuestion` to switch to `/z-maintain-docs`, continue anyway, or abandon. It does NOT auto-invoke `/z-maintain-docs`.
- `/z-uplift` is resumable via MANIFEST.md state: `[ ] pending` or `[~] auditing` rows resume at Phase 3; `[a] audited` rows resume at Phase 5. Use `--retry-bailed` to reset `[!] bailed` rows back to pending, and `--refresh-component <slug>` to re-audit a single named component.
- `perf` is excluded from `/z-uplift`'s default `--dimensions` set (`correctness,cleanliness,design`) to bound cost; pass `--dimensions=correctness,cleanliness,design,perf` to include it explicitly.
- The cross-cutting synthetic component (`<slug>-cross-cutting`) is inserted as the first MANIFEST row and is excluded from Phase 3 per-component audit iteration; it is handled separately in Phase 5.
- `/z-uplift` slug collision detection runs after decomposition: if two components share a slug, an `AskUserQuestion` is raised per collision before COMPONENTS.md is finalized and MANIFEST.md is written.
- `/z-style-init` Mode A refuses if `STYLE.md` already exists at repo root; use `--amend` or delete manually.
- `/z-style-init` Mode B (`--amend`) exits early if no dismissal signatures are found or no clusters have at least 2 members. The "add-with-edits" interactive free-text flow is deferred to v2; users must reject and manually edit STYLE.md to customize proposed rules.
- `/z-style-init` Phase 4 dispatches both `consultant-secondary` and `consultant-primary` in parallel; if one errors, the other's findings are applied alone. Both failing causes critique to be skipped with a log event.
- `/z-providers-discover` enforces `consultant_primary != consultant_secondary`; it reprompts until the constraint is satisfied or one role is unbound. Role collision detection uses last-assignment-wins for multi-CLI selections.
- `/z-export` continues past individual target failures — a failed `cursor` export does not abort the `codex` or `agy` exports. All output is verbatim from adapter scripts; the command does no LLM interpretation of export results.
- `/z-export` defaults to `--target=all`; unrecognized target values exit nonzero immediately before running any scripts.
- `/z-audit-plan-style` has a hard STYLE.md gate: there is no `--no-style` escape. If STYLE.md is missing, the command refuses immediately and routes to `/z-style-init`.
- `/z-audit-plan-style` emits `PLAN_STYLE_AUDIT.md` separately from `/z-audit-plan`'s `PLAN_AUDIT_REPORT.md`; correctness findings from the plan-style-reviewer are passed through under a `## Cross-dimension note` but are not promoted into amendment blocks.
- `/z-audit-plan-style` archives any existing `PLAN_STYLE_AUDIT.md` before overwriting — this archive is what `extract-dismissals.py` reads to compute prior dismissal signatures on subsequent runs.
- `/z-audit --scope-from` must be parsed before slug derivation, doc-fetcher dispatch, or `run_start` logging. SCOPE_FROM_ERROR is stored for deferred halt after Setup establishes RUN.
- `/z-audit` HEAVY fan-out always uses absolute-path-with-fragment form (`/abs/path/SCOPE.json#C1`) in sub-flow prompts. Bare chunk IDs (`C1`) are for manual invocation only and require `PARENT_RUN_ID` and `PARENT_SLUG` in the caller context.
- `/z-audit` HEAVY path skips Phase 2 (auditor dispatch) and Phase 3 (merge findings) entirely; the reconciler has already written REPORT.md. Attempting to run Phase 2/3 in the HEAVY path will fail because per-dimension findings files do not exist.
- `/z-audit` HEAVY chunk-artifact path validation: `dest` must be under `chunks_dir`; absolute `source` paths must start with `Z_HARNESS_PLAN_DIR` OR one of the per-chunk findings_path parent directories from the sub-flow archive.
- `/z-brainstorm` Phase 0 axis taxonomy is `[per_vendor, per_framing]`. Low-confidence probe results are silently downgraded to MEDIUM in v1a with no user gate.
- `/z-brainstorm` Phase 2a is a complete no-op when `brainstorm.personas` is OFF — no draw, no prefix, no `persona_bound` event, no change to `ideator_personas` beyond recording `<none>` for each slot. Phase 2b dispatch is byte-identical to pre-persona behavior.
- `ideator_personas` in BRAINSTORM.md frontmatter is always written in Phase 3, even when the `brainstorm.personas` knob is OFF (all three values record `<none>`) or when an ideator failed (the persona binding is still recorded; the `ideators` list separately appends `:failed`).
- The persona prefix in `/z-brainstorm` Phase 2a is a prompt-only concern: it does not change the model, runtime, or `subagent_type` for any ideator. Vendor diversity and persona diversity are orthogonal — all three ideators still receive byte-identical scaffolding and `IDEATOR_SCHEMA` instructions.
- `/z-brainstorm` HEAVY sub-flows skip Phase 0 entirely (anti-sprawl invariant). Sub-flows run only Phases 1, 2, and 3 for their chunk's sub-scope, writing per-chunk BRAINSTORM.md files to archive chunks directories.
- `/z-brainstorm` HEAVY Phase 4: N_PAIRS ≤ 12 uses a single AskUserQuestion for all (chunk, framing) pairs; N_PAIRS > 12 uses a two-step question (chunk first, then framing). Back-loops are capped at 3 iterations; the fourth Back is treated as Abandon.
- `/z-brainstorm` HEAVY abandons set `chosen_framing: abandoned` (not `chosen_pair`) so abort detection is uniform across LIGHT/MEDIUM/HEAVY modes.
- `/z-plan` step 9c consolidated freshness gate: the proceed-with-all-stale and abandon choices both set `to_command: null` in `plan_route_decision` — this is how `/z-stats` distinguishes them from a real remedy-command route. The `precontext_freshness_acknowledged` event is emitted only when `research_stale` or `map_stale` is true (not for docs-only staleness).
- `/z-research` Phase 1 parallel dispatch: when both `DISPATCH_MAP=ran` and `DISPATCH_BRAINSTORM=ran`, both Agent() calls are issued in a single message. Sub-run archive identification uses the first event's `kind` field in each archive's `events.jsonl` (`map_run_start` vs `brainstorm_run_start`) rather than directory name, which is robust against same-second RUN-ID timestamp collisions. If identification fails (both resolve to same dir, or either is missing), the orchestrator aborts rather than guessing.
- `/z-implement-all` N=2 cross-cluster parallel dispatch fires only when `overlap_count == 0` in SHARED-CONCERNS.md; plans with any overlap always run serially. N=3 parallel cross-cluster dispatch is a v2 concern.
- `/z-implement-all` cycle-2 skip-on-clean-cycle-1: the guard fires regardless of the reason the implementer re-ran (e.g., clarification resolved, design decision answered). A clean cycle-1 means no review-side issue exists; re-reviewing cannot surface new findings from that same diff.
- Notification policy across all commands now points to `docs/human/config.md` (not a `Z_HARNESS_NOTIFY` env var). Commands that send notifications call `scripts/config.py should-notify --event <type>` and act only when the return is `yes`. `/z-do` and `/z-plan` also call `scripts/config.py export-env` during Setup to hydrate all config knobs into the environment before any phase runs.
- Resolver hooks (`resolve-question`) are separate from notification policy: they govern AskUserQuestion gates, not notification sends. A resolver error (any non-zero exit) always falls back to asking the user normally — never silently skips.
- The hard slug-collision check (detecting an existing PLAN.md/TASKS.md in the slug dir) always runs unconditionally in `/z-plan`, `/z-fix`, and `/z-uplift` before the resolver is consulted. The resolver only governs the soft non-obvious-slug confirmation gate that runs after the collision check passes.
- Elevation proposer Phase 9 in `/z-audit-plan`, `/z-audit-plan-style`, and `/z-amend` is a soft phase: if `propose-prefs.py` returns empty output or a non-zero exit, the phase is skipped silently with no AskUserQuestion surfaced.
- Suppression entries in `.z-harness/.propose-suppress` are keyed by `question_id` with a Unix-epoch expiry. The elevation proposer checks these before surfacing a proposal; an unexpired entry suppresses the proposal entirely.
- `/z-suggest-memory --kind routing-preference` writes to `docs/llm/workflow.json` (global) or `docs/llm/workflow-<project-slug>.json` (project scope). The file is created with INDEX.json registration if it does not exist. The `reason` and `project_root` fields are omitted from the entry when not applicable. MEMORIES-FLAT.md is regenerated after every write.
- `check-no-ask` is fail-closed for overnight: it handles the `Z_HARNESS_ASK_ALL=1` + `Z_HARNESS_NO_ASK=halt` conflict as exit code 5; commands treat exit 5 as a hard config-conflict error (not a silent skip). A resolver error (non-zero exit from `resolve-question`) falls back to asking the user normally; `check-no-ask` exit codes are distinct and must not be conflated with `resolve-question` error paths.
- `/z-overnight` sets `Z_HARNESS_NO_ASK=halt` ONLY immediately around each Skill call; the parent orchestrator's own `AskUserQuestion` prompts (lock contention, already-complete resume) run with `NO_ASK` unset. Hard halts (slug collision detected by `overnight-preflight.sh`, lock corruption, state-file corruption, empty chain) are never bypassed by the allowlist.
- `/z-overnight` sub-run archive identification uses a snapshot diff of `$BASE/archive/` directories, excluding dirs whose basename matches `*-overnight-*`. If `NEW_COUNT == 0` or `NEW_COUNT > 1`, the step is set to `error` and a `run_id_ambiguous` event is emitted.
- `/z-overnight` resume HEAD SHA validation: if HEAD has changed since the last completed step, a CRITICAL warning is printed and execution proceeds anyway — it does NOT halt.
- `/z-review-all` `check-no-ask` halt writes a partial `.review_state.json` with `halted: true` and `halt_reason: "no_ask_blocked"`. Re-invocation must detect this before Phase 0 (not after); if detected, emit `review_resume_from_halt` and jump directly to Phase 3.7.
- The `workflow.plan_decisions_approval` resolver gate in `/z-plan` is distinct from the slug-confirm gate: it governs the decisions-doc approval step (Phase 2.5) and has its own `check-no-ask` + `halt` branch emitting `plan_halt` with `question_id: "workflow.plan_decisions_approval"`. A subsequent `/z-plan` resume re-enters at Phase 2.5.
- The Phase 0 consumer check in `z-implement-all`, `z-implement-next`, and `z-review-all` reads `index.view.json` as a dict with an `entries` object (not a list); the T100 fix ensures the parse uses `entries_obj.values()` rather than iterating `entries` as a list directly. A missing or malformed `index.view.json` is treated as zero running entries (safe-default, never halts).
- All six `/z-followup-*` commands carry a nest guard (`Z_HARNESS_FOLLOWUP_CALLER_DEPTH >= 1`) that fires before any other logic. This prevents listing or modifying sink state from within an executing follow-up entry's recommended command.
- `/z-followup-next` is the only followup command that acquires per-entry locks. It checks the global cross-tool lock (`$HOME/.z-harness/.followup-vs-implement.lock`) before claiming any entry; if already held, it halts rather than racing.
- `/z-followup-confirm --via=audit` requires `--evidence=<path>` pointing to an `audit_evidence.json` blob; `--via=human` is mutually exclusive with `--evidence`. Mixing the flags is a hard argument-parse error.
- `/z-followup-refresh` is only valid for `blocked` entries whose block reason is staleness. Entries blocked for other reasons (e.g., dependency-blocked) are rejected with an explicit error message.
- `/z-review-all` Phase 3.7.5 sink writes are best-effort: per-entry errors (non-zero `sink-add.sh` exit) are logged and skipped; the routing step never blocks the review pipeline. If `scripts/sink-add.sh` is not yet present, the step is silently skipped.
- `Z_HARNESS_CONSULT=off` is detected in `/z-plan` (Phases 3 and 7) and `/z-implement-all` (Steps 6 and 7a) by calling `scripts/resolve-provider.py` and checking for the `none` sentinel; it is NOT a raw env-var check. Setting the env var without a provider config that causes `resolve-provider.py` to return `none` has no effect.
- When `Z_HARNESS_CONSULT=off`, `/z-plan` Phases 3 and 7 each emit a separate `consult_skipped` event keyed by `phase`. `/z-implement-all` emits `no_consult_dispatch` per task-cycle (not once per run) and `self_review_completed` after each self-review returns. These are distinct events — do not conflate them.
- The `self-reviewer` subagent dispatched by `/z-implement-all` when consult=off is read-only (no Edit/Write tools) and uses the same response-shape as the standard `reviewer`, so Step 7 branching (blockers/majors counts) works identically for both paths.
- Active-plan registry: `REG_RC == 3` means register FAILED — no record was written. The orchestrator logs `registry_error` and branches (interactive: ask proceed/abort; unattended: proceed+log or halt if `Z_HARNESS_STRICT_OVERLAP=1`). If register failed, do NOT call deregister anywhere in the run (no record exists). `REG_RC == 0` means registered — FINALIZE_STATUS rule applies from this point forward.
- Active-plan overlap scan: `OVL_RC == 0` (no overlap) proceed silently; `OVL_RC == 10` (advisory overlap) present via AskUserQuestion: proceed / wait / abort; `OVL_RC == 20` (blocking — strict mode only, exact path match) hard halt; any other nonzero log `registry_error` and proceed (inconclusive degrades to uncoordinated). The registry self-emits `active_plan_scan_complete` / `scope_overlap_detected`.
- `/z-where` does not log a start/end event for itself — it is intentionally telemetry-free. The overlap query exit codes it renders are the same codes `active-plan-registry.py overlaps` returns (0/10/20/other).
- `/z-stats` Phase 0b active-plan count is read unconditionally (NOT gated behind `Z_HARNESS_EXPLAIN_RESOLUTION` or any other env var). If the registry call fails, it prints `Active plans: (registry unavailable)` and continues.
- The `scope-extractor` subagent used by run-creating commands (z-plan Phase 8, z-implement-all Phase 0.0, z-implement-next Phase 0.0, etc.) is best-effort non-fatal: `update-scope` returns 0 by design and self-logs `registry_error` on internal failure; the orchestrator calls it with `|| true`.
- `/z-plan` heartbeat fires at the Phase 8 boundary (after TASKS.md and complexity stamps are finalized, before scope seed completes). It is best-effort non-fatal (`|| true`).
