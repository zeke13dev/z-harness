# z-harness project rules

This root `AGENTS.md` is intentionally small. Oh My Pi and other coding agents auto-load root `AGENTS.md` as startup context; do not inline the full z-harness agent catalog here.

## Agent catalog

- Source agent definitions live in `agents/*.md`.
- Command and skill procedures live in `skills/*/SKILL.md`.
- CLI command modules live in `z_harness_cli/commands/*.py`; runtime/export drivers live under `runtime/`.
- Host-specific exports are generated on demand under the requested output directory (default `temp/exports/`), not committed as release source.

If a task needs a specific agent's behavior, read only that agent file. Do not preload the whole catalog.

## Export note

The large consolidated Codex `AGENTS.md` is generated by the Codex export driver for Codex-only installs. Generate it into `temp/exports/` or another scratch/export directory; do not commit it at repo root.

## Branch policy

- `main` is the research/development branch. Keep experimental command work there until it is explicitly promoted.
- `prod` is the public-release branch. Only promote commands, agents, docs, and install surfaces to `prod` after release-readiness review and targeted verification.
- When changing `/z-research`, `/z-map`, `/z-overnight`, `/z-attend`, `z-axiom-*`, or other experimental surfaces, assume the work belongs on `main` unless the task explicitly says to prepare a `prod` promotion.

## prod branch workflow

- Develop normally on `main`; it may contain research, experimental, and release-prep work.
- Use `prod` only as the public-release branch. Do not develop directly on `prod`.
- To cut or refresh `prod`, start from a clean `main`, switch to `prod`, cherry-pick or re-stage only release-ready changes, then run targeted verification before committing.
- Keep main-only experiments off `prod` unless they are explicitly promoted as part of a release-readiness pass.
- Push `prod` only after the release commit is reviewed and the working tree is clean.

## Operating rules

- **Worktree-only edits:** Every agent must make content edits only in a linked
  worktree. Before editing, confirm the primary worktree is checked out on
  clean local `main`, then create or select a topic branch from that `main`.
  Do not edit, commit ordinary changes, or push from the primary checkout.
  Reserve it for read-only inspection, worktree creation, and safe merges of
  verified branches. If it is dirty, stop and ask the owner to resolve it;
  never stash, discard, or absorb someone else's changes to make progress.
- After validation, merge the completed worktree branch into clean local
  `main`; do not push `main` as part of an agent task unless the user explicitly
  authorizes it. In qt-bot, required compile/test checks run in the external
  sandbox before the merge.
- Prefer targeted reads and searches over broad file dumps.
- Use existing z-harness source conventions; do not invent a parallel workflow.
- No emojis in generated code, docs, or reports unless explicitly requested.
